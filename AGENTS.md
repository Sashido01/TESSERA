# Правила работы с TESSERA

[**Русский — оригинал**](AGENTS.md) | [English — перевод](AGENTS.en.md)

TESSERA — отдельный публичный каталог Agent Skills. Канонический репозиторий: `Sashido01/TESSERA`.

1. Сначала изучи README, правила проекта и существующие навыки. Не путай проект TESSERA с приложением, которое использует отдельный навык.
2. Каждый навык размещается в `skills/<имя>/SKILL.md`; имя в метаданных должно совпадать с именем каталога. Сохраняй совместимость со спецификацией Agent Skills.
3. Оставляй навыки независимыми: если требуются отдельные интеграции для Harness, Codex или другой среды, храни их отдельно и не обещай автоматическую активацию без проверок.
4. После изменений выполни `python tools/validate_skills.py`, `python tools/check_public_paths.py`, `python tools/check_translations.py`, `python tools/check_repository_version.py`, `python -m unittest discover -s tests -v` и тесты затронутого навыка. Записывай точный результат.
5. **Та же микроверсионность обязательна и для TESSERA, а не только для навыков.** Исторический старт — `0.0.0`, первая обязательная рабочая микроверсия — `0.0.1`. После каждого самостоятельного проверенного изменения увеличивай корневой `VERSION` на PATCH+1 и обновляй обе версии CHANGELOG в том же коммите. По достижении `.99` после завершения задачи и проверок выпускай следующий `.0` релиз. Если задача не закончена — продолжай `.100`, `.101` и далее до реального завершения. Не создавай фиктивных коммитов и не переписывай старую историю. Правила: [VERSIONING.md](docs/VERSIONING.md).
6. Коммиты и описания изменений пиши понятно, конкретно, по-русски. Не заявляй о выполненных тестах, сборках и публикациях без фактических доказательств.
7. Не загружай секреты, закрытые конфигурации, личные данные, абсолютные пути к рабочим каталогам владельца и файлы других проектов. Локальные пути используйте только для работы в своей среде, но никогда не включайте их в публичные README, инструкции, примеры, сообщения коммитов или релизов. В публичных примерах используйте нейтральные плейсхолдеры (`<project-root>`, `<skills-dir>`). Не делай `push --force`, перемещение чужих тегов или уничтожающие операции с Git.
8. **Для каждого релиза TESSERA и каждого вложенного навыка аннотированный Git-тег обязателен.** После успешного CI для коммита `main` создаётся аннотированный Git-тег каталога `vX.Y.Z` с понятным русским описанием; у независимых навыков могут быть теги `<skill>/vX.Y.Z`. Проверь, что тег аннотирован и указывает на точный коммит релиза. Без подтверждённого тега релиз `BLOCKED / RELEASE_NOT_TAGGED`. Не передвигай существующие теги. Выпуск GitHub Release и изменение настроек удалённого репозитория — отдельные действия; не считай наличие тега опубликованным приложением.
9. Не изменяй старую опубликованную историю версий. При конфликте правил между навыком и действующим проектом сохрани проектные ограничения и обозначь конфликт.
10. Перед завершением сообщи фактические версии, коммиты, тесты, изменения и остающиеся ограничения.
11. **Языковой приоритет:** `README.md`, `AGENTS.md`, `SKILL.md` и другая основная документация создаются на русском языке. Английские переводы размещаются в `*.en.md` и обновляются в том же изменении. Для `SKILL.md` перевод хранится в `references/SKILL.en.md` без frontmatter. Подробности: [docs/I18N.md](docs/I18N.md).
12. Стандартный навык должен оставаться переносимым между Codex, Harness, Claude Code, Hermes и другими Agent Skills-совместимыми системами. Не добавляй обязательных vendor-only полей в SKILL.md. Отдельные интеграции и инструкции установки — после проверки официального формата; при непроверенном локальном запуске укажи `NOT_VERIFIED`.
13. **Обязательные архитектурные решения:** соблюдай [docs/DEPENDENCIES.md](docs/DEPENDENCIES.md) и [docs/ROADMAP.md](docs/ROADMAP.md). Не вводи сторонние менеджеры навыков в утверждённую архитектуру. Не используй NVIDIA SkillEvaluator Tier 2/3 и обязательные платные AI API. GitHub CLI — предпочтительный будущий установщик только после испытаний; Python — минимальный офлайн-резерв. Планируй единое ядро Release Core с тонкими адаптерами, а не четыре самостоятельных ядра.
14. Правила GitHub Rulesets и статические проверки CI — не одно и то же. Цикл PR → CI → squash merge → аннотированный тег подтверждён. T08 остаётся PARTIAL только из-за непроверенных опасных отрицательных сценариев изменения тегов и обхода защиты. Не проводи разрушительных тестов над опубликованными тегами. См. [docs/GITHUB_SECURITY.md](docs/GITHUB_SECURITY.md).
15. Для T09.02 применяй `core/release_preflight.py` сначала в режиме `--plan`. Режим `--execute` допускается только для доверенного проекта после явного разрешения и аудита `release-checks.json`. Не запускай команды из неизвестного Pull Request автоматически; PASS проверок не заменяет Git-тег и не означает RELEASED. См. [docs/RELEASE_PREFLIGHT.md](docs/RELEASE_PREFLIGHT.md).
16. T09.03: после подтверждённого аннотированного тега проверь объект тега на доверенном remote командой `core/release_report.py --verify-remote` и получи фактологический JSON/Markdown. Не запускай `--execute-checks` без явного разрешения; не называй `evidence_status=PASS` готовностью или публикацией приложения. См. [docs/RELEASE_REPORT.md](docs/RELEASE_REPORT.md).
17. T09.04: независимую проверку GitHub Actions выполняй только после **завершения всего workflow** с явным `--verify-ci --github-repo <owner/repo> --run-id <id>`. Сверяй полный SHA, правильный workflow и обе обязательные jobs; не вводи круговую проверку внутри ещё работающего job. Успешный CI не равен опубликованному приложению. См. [docs/RELEASE_CI.md](docs/RELEASE_CI.md).
18. T09.05: проверяй GitHub Release отдельно от тега и CI. По умолчанию не обращайся к сети; `--verify-publication` требует доверенный GitHub-репозиторий и совпадающий Git remote. Не создавай GitHub Release автоматически, не называй metadata assets проверкой их содержимого. `--format certificate` выдаёт неподписанное свидетельство с воспроизводимым SHA-256, а не криптографическую аттестацию. См. [docs/RELEASE_PUBLICATION.md](docs/RELEASE_PUBLICATION.md).
19. T09.06: `--verify-assets` требует явного согласованного `--verify-publication`; проверяй размер и SHA-256 **скачанных байтов**, а не только поле digest GitHub. Без прикреплённых файлов не выдавай PASS. Не открывай произвольные URL и не разрешай перенаправления на посторонние домены, не записывай активные локальные пути в публичный репозиторий. Даже при совпадении SHA `artifact_provenance` и `release_readiness` остаются NOT_VERIFIED. См. [docs/RELEASE_ASSETS.md](docs/RELEASE_ASSETS.md).
20. T09.07: не называй совпадение SHA-256 независимой аттестацией. Для происхождения используй только официальный `gh attestation verify` по явному `--verify-provenance` с подтверждённым release asset, `--artifact-file`, `--signer-workflow`, exact SHA коммита и Git-тегом. В отсутствие опубликованного подписанного файла ставь NOT_VERIFIED; не создавай фиктивный GitHub Release. Итоговый JSON-сертификат всё ещё неподписан. См. [docs/RELEASE_PROVENANCE.md](docs/RELEASE_PROVENANCE.md).
21. Git-ветки: одна короткоживущая рабочая ветка на логически связанную цель и один проверяемый Pull Request; при сбое CI исправляй **ту же** ветку, не создавай новую для каждого шага. Отдельная микроверсия и обязательный тег — у завершённого результата, принятого в `main`. См. [docs/BRANCHING.md](docs/BRANCHING.md).
22. T09.08: `tools/build_catalog_package.py` создаёт детерминированный ZIP **каталога**, не самостоятельную версию вложенного навыка. Доверенная attestation создаётся только ручным `workflow_dispatch` по проверенному аннотированному тегу через [build-attested-catalog.yml](.github/workflows/build-attested-catalog.yml). В PR этот workflow ничего не подписывает; автоматического GitHub Release нет. Без фактического signing run результат NOT_VERIFIED. См. [docs/TRUSTED_BUILD.md](docs/TRUSTED_BUILD.md).
23. T09.09: для проверки фактического ZIP используй `tools/verify_catalog_package.py` с независимо установленными версией и полным SHA исходного коммита. PASS означает лишь внутреннюю целостность по манифесту, а не происхождение, подпись или публикацию. Никакой распаковки ZIP или исполнения содержимого. См. [docs/CATALOG_VERIFICATION.md](docs/CATALOG_VERIFICATION.md).
24. T09.10: не используй `gh attestation verify` и `gh run download` из GitHub CLI ниже `2.102.0`: опубликованы уязвимости проверки signer/source-ref и скачивания через symlink. `core/release_provenance.py` обязан отвергать старую или неизвестную версию. Реальную подпись, артефакт и независимую приёмку нельзя заменять тестовыми ответами CLI. См. [docs/RELEASE_PROVENANCE.md](docs/RELEASE_PROVENANCE.md).

25. T11.01: вместе с собственным валидатором обязателен эталонный `skills-ref` по фиксированному commit SHA и хешированным зависимостям. Не путай проверку формата со способностью конкретного агента загрузить навык. Reference-библиотека upstream — демонстрационная; использовать её как единственный production-контроль запрещено. Подробности: [docs/AGENT_SKILLS_STANDARD.md](docs/AGENT_SKILLS_STANDARD.md).

26. T08.01: не заменяй закреплённые SHA GitHub Actions плавающими `@vN` и не возвращай устаревшие Node.js 20 versions. `tools/check_actions_runtime.py` должен блокировать неизвестные и изменённые Actions в обычном и подписывающем workflow. Изменения Actions допускаются только после проверки официального релиза, SHA, runtime и полного CI; это не подтверждает реальную подпись. См. [docs/GITHUB_SECURITY.md](docs/GITHUB_SECURITY.md).

27. T11.02: при проверке `gh skill publish --dry-run` используй только проверенный по SHA-256 официальный CLI, временную копию `skills/` без GitHub remote, наследованных токенов или пользовательской конфигурации. Не запускай `gh skill publish` без `--dry-run` и никогда не вызывай `--fix` в CI. Проверяй позитивный и негативный сценарий и неизменность файлов; локальный PASS не доказывает реальную публикацию. См. [docs/GH_SKILL_PUBLISH_DRY_RUN.md](docs/GH_SKILL_PUBLISH_DRY_RUN.md).

28. T10.01: в локальном `gh skill install --from-local` официальная версия `2.105.0` может перезаписывать файлы уже существующего каталога даже без `--force`. Перед вызовом CLI обязательная проверка отсутствия целевого каталога; проверка проводится только во временном профиле и директории. `--pin` и `--from-local` взаимоисключающие; не заявляй привязку по тегу для локальной копии. Реальная установка из GitHub по SHA и тегу относится к T10.02. См. [docs/GH_SKILL_INSTALL.md](docs/GH_SKILL_INSTALL.md).

29. T09.10.01: подписывающий workflow выполняет Python-тесты до ZIP-сборки. Обязательно `PYTHONDONTWRITEBYTECODE=1` в signing и validate; основной CI дополнительно собирает ZIP **после** тестов. `scripts/__pycache__` запрещён, расширять allowlist ради временного байткода нельзя. Не считать исправление подтверждением Sigstore-подписи. Фактический сбой: [Actions 45347443989](https://github.com/Sashido01/TESSERA/actions/runs/45347443989); [TRUSTED_BUILD](docs/TRUSTED_BUILD.md).
30. T09.10 COMPLETE: [реальная приёмка v0.0.21](docs/TRUSTED_BUILD.md) подтверждает конкретный подписанный ZIP. Не переносить `SIGNED_ARTIFACT=PASS` на новый SHA или тег. Последующие пакеты требуют самостоятельного скачивания, SHA-256, проверки манифеста и независимой проверки Sigstore через безопасную версию `gh`. Actions Artifact не равен GitHub Release.
31. T10.02: для удалённого pin используй полный refs/tags/vX.Y.Z и проверенный commit SHA, не короткое имя (приоритет веток). Проверяй ожидаемое Git tree и реальные установленные файлы в новом временном каталоге. Только read-only CI token; не передавай его Git и не выводи сырые ошибки CLI. Не используй --force или --unpin в профиле пользователя. См. [docs/GH_SKILL_INSTALL.md](docs/GH_SKILL_INSTALL.md).
