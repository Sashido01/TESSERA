# Правила работы с TESSERA

[**Русский — оригинал**](AGENTS.md) | [English — перевод](AGENTS.en.md)

TESSERA — отдельный публичный каталог Agent Skills. Канонический репозиторий: `Sashido01/TESSERA`.

1. Сначала изучи README, правила проекта и существующие навыки. Не путай проект TESSERA с приложением, которое использует отдельный навык.
2. Каждый навык размещается в `skills/<имя>/SKILL.md`; имя в метаданных должно совпадать с именем каталога. Сохраняй совместимость со спецификацией Agent Skills.
3. Оставляй навыки независимыми: если требуются отдельные интеграции для Harness, Codex или другой среды, храни их отдельно и не обещай автоматическую активацию без проверок.
4. После изменений выполни `python tools/validate_skills.py`, `python tools/check_public_paths.py`, `python tools/check_translations.py`, `python tools/check_repository_version.py`, `python -m unittest discover -s tests -v` и тесты затронутого навыка. Записывай точный результат.
5. **Та же микроверсионность обязательна и для TESSERA, а не только для навыков.** Исторический старт — `0.0.0`, первая обязательная рабочая микроверсия — `0.0.1`. После каждого самостоятельного проверенного изменения увеличивай корневой `VERSION` на PATCH+1 и обновляй обе версии CHANGELOG в том же коммите. По достижении `.99` после завершения задачи и проверок выпускай следующий `.0` релиз. Если задача не закончена — продолжай `.100`, `.101` и далее до реального завершения. Не создавай фиктивных коммитов и не переписывай старую историю. Правила: [VERSIONING.md](docs/VERSIONING.md).
6. Коммиты и описания изменений пиши понятно, конкретно, по-русски. Не заявляй о выполненных тестах, сборках и публикациях без фактических доказательств.
7. Не загружай секреты, закрытые конфигурации, личные данные, абсолютные пути к рабочим каталогам владельца и файлы других проектов. Локальные пути используйте только для работы в своей среде, но никогда не включайте их в публичные README, инструкции, примеры, сообщения коммитов или релизов. В публичных примерах используйте нейтральные плейсхолдеры (`<project-root>`, `<skills-dir>`). Не делай `push --force`, перемещение чужих тегов или уничтожающие операции с Git.
8. **Для каждого релиза TESSERA и каждого вложенного навыка аннотированный Git-тег обязателен.** После успешного CI для коммита `main` создаётся аннотированный Git-тег каталога `vX.Y.Z` с понятным русским описанием; у независимых навыков могут быть теги `<skill>/vX.Y.Z`. Проверь, что тег аннотирован и указывает на точный коммит релиза. Без подтверждённого тега релиз `BLOCKED / RELEASE_NOT_TAGGED`. Не передвигай существующие теги. Выпуск GitHub Release и изменение настроек удалённого репозитория — отдельные действия; не считай наличие тега опубликованным приложением.
9. Не изменяй старую опубликованную историю версий. При конфликте правил между навыком и действующим проектом сохрани проектные ограничения и обозначь конфликт.
10. Перед завершением сообщи фактические версии, коммиты, тесты, изменения и остающиеся ограничения.
11. **Языковой приоритет:** `README.md`, `AGENTS.md`, `SKILL.md` и другая основная документация создаются на русском языке. Английские переводы размещаются в `*.en.md` и обновляются в том же изменении. Для `SKILL.md` перевод хранится в `references/SKILL.en.md` без frontmatter. Подробности: [docs/I18N.md](docs/I18N.md).
12. Стандартный навык должен оставаться переносимым между Codex, Harness, Claude Code, Hermes и другими Agent Skills-совместимыми системами. Не добавляй обязательных vendor-only полей в SKILL.md. Отдельные интеграции и инструкции установки — после проверки официального формата; при непроверенном локальном запуске укажи `NOT_VERIFIED`.
13. **Обязательные архитектурные решения:** соблюдай [docs/DEPENDENCIES.md](docs/DEPENDENCIES.md) и [docs/ROADMAP.md](docs/ROADMAP.md). Не вводи сторонние менеджеры навыков в утверждённую архитектуру. Не используй NVIDIA SkillEvaluator Tier 2/3 и обязательные платные AI API. GitHub CLI — предпочтительный будущий установщик только после испытаний; Python — минимальный офлайн-резерв. Планируй единое ядро Release Core с тонкими адаптерами, а не четыре самостоятельных ядра.
14. Правила GitHub Rulesets и статические проверки CI — не одно и то же. Цикл PR → CI → squash merge → аннотированный тег подтверждён. T08 остаётся PARTIAL только из-за непроверенных опасных отрицательных сценариев изменения тегов и обхода защиты. Не проводи разрушительных тестов над опубликованными тегами. См. [docs/GITHUB_SECURITY.md](docs/GITHUB_SECURITY.md).
15. Для T09.02 применяй `core/release_preflight.py` сначала в режиме `--plan`. Режим `--execute` допускается только для доверенного проекта после явного разрешения и аудита `release-checks.json`. Не запускай команды из неизвестного Pull Request автоматически; PASS проверок не заменяет Git-тег и не означает RELEASED. См. [docs/RELEASE_PREFLIGHT.md](docs/RELEASE_PREFLIGHT.md).
16. T09.03: после подтверждённого аннотированного тега проверь объект тега на доверенном remote командой `core/release_report.py --verify-remote` и получи фактологический JSON/Markdown. Не запускай `--execute-checks` без явного разрешения; не называй `evidence_status=PASS` готовностью или публикацией приложения. См. [docs/RELEASE_REPORT.md](docs/RELEASE_REPORT.md).
17. T09.04: независимую проверку GitHub Actions выполняй только после **завершения всего workflow** с явным `--verify-ci --github-repo <owner/repo> --run-id <id>`. Сверяй полный SHA, правильный workflow и обе обязательные jobs; не вводи круговую проверку внутри ещё работающего job. Успешный CI не равен опубликованному приложению. См. [docs/RELEASE_CI.md](docs/RELEASE_CI.md).
