# T09.05 — проверка публикации и свидетельство доказательств

[**Русский — оригинал**](RELEASE_PUBLICATION.md) | [English — перевод](RELEASE_PUBLICATION.en.md)

## Что подтверждается

Публичный каталог Agent Skills различает **коммит с успешным CI**, **аннотированный Git-тег**, **GitHub Release с исходниками** и **проверенный бинарный/установочный артефакт**. Это разные факты. Наличие тега `vX.Y.Z` не доказывает публикацию GitHub Release. Публикация GitHub Release не доказывает доставку или работоспособность конечного приложения.

По состоянию на 23.11.2026 на публичном GitHub `Sashido01/TESSERA` существуют аннотированные теги до `v0.0.10`, но **список GitHub Releases пуст**. Нельзя объявлять прежние микроверсии полноценными GitHub Releases.

Реализованы `core/release_publication.py` (независимое чтение metadata GitHub Release) и `core/release_certificate.py` (воспроизводимое неподписанное свидетельство результатов проверок). Ни один компонент не публикует GitHub Release автоматически.

## Два вида подтверждения

**Тег и CI:** `TAG_AND_CI_VERIFIED` означает совпадение аннотированного тега на доверенном remote и успешный завершённый GitHub Actions по точному SHA. Это ещё не GitHub Release.

**Публикация исходников:** `SOURCE_RELEASE_PUBLISHED` в свидетельстве возможен только когда дополнительно проверен реальный опубликованный GitHub Release того же тега, нет draft/prerelease, совпадают доверенный удалённый GitHub-репозиторий и все предыдущие доказательства. GitHub автоматически предоставляет исходный архив для публичного Release; **данный инструмент не скачивает его и не проверяет байты**. Для исполняемых программ наличие Release всё ещё не доказывает установку, подпись бинарника или корректность файлов.

## Команды

Из корня проверяемого Git-репозитория:

```bash
# По умолчанию никакой сети: вывод обычного отчёта о доступных локальных данных.
python core/release_report.py --repo . --version 0.0.11

# Запрос GitHub Release и независимых доказательств после завершения CI.
python core/release_report.py --repo . --version 0.0.11 \
  --verify-remote --verify-ci --verify-publication \
  --github-repo owner/repository --run-id 123456789 \
  --format certificate

# Вывод отчёта для человека, без сетевых запросов.
python core/release_report.py --repo . --version 0.0.11 --format markdown
```

Это примеры синтаксиса: `owner/repository`, `123456789` и `0.0.11` нужно заменить на реально проверяемый репозиторий, завершённый run ID и опубликованную версию. По умолчанию нет запросов к API, сетевой проверки Git или запуска команд проекта. Для выполнения команд релизного плана по-прежнему требуется отдельное `--execute-checks`. Не запускать команды из недоверенных Pull Requests.

## Независимая проверка GitHub Release

При **явном** `--verify-publication` выполняется GET к официальному `api.github.com/repos/{owner}/{repo}/releases/tags/{tag}`. Проверяются:

- корректный точный тег и идентификатор опубликованного Release;
- `draft=false`, `prerelease=false`, дата `published_at` и страница Release на соответствующем GitHub-репозитории;
- список assets: уникальные имена, `state=uploaded`, положительный размер и корректный синтаксис `digest` при его наличии;
- связь переданного `--github-repo` с фактическим Git remote `origin` (или выбранным именованным remote) через HTTPS/SSH URL GitHub;
- совместимость фактов Release с локальным аннотированным тегом, результатом проверки его remote и завершённым CI.

**Важный нюанс:** поле GitHub `target_commitish` нельзя использовать как независимое доказательство коммита: оно может содержать название ветки, а не SHA. Надёжное соответствие коммиту задаётся отдельно проверенными объектами Git-тегов.

Если опубликованный Release отсутствует или недоступен, запрос заблокирован или вернул неполные данные, результат `PUBLICATION_QUERY_FAILED_OR_MISSING / BLOCKED`. Инструмент не делает вид, что публикация состоялась. Draft и prerelease не считаются стабильным выпуском.

## Доказательное свидетельство

`--format certificate` формирует JSON со схемой версии 1, проверяемой версией, SHA коммита и тега, результатами CI и Git remote, данными GitHub Release и полями `publication_evidence_status`, `application_release_readiness`, `signed`.

- `SOURCE_RELEASE_PUBLISHED`: реально подтверждён исходный GitHub Release, успешный CI и точный объект тега на remote.
- `TAG_AND_CI_VERIFIED`: нет запроса к публикации, но подтверждены CI и удалённый тег.
- `INCOMPLETE`: для выбранной полноты свидетельства не хватает доказательств.
- `BLOCKED`: обнаружены противоречащие данные или ошибка обязательной запрошенной проверки.

Свидетельство содержит `evidence_sha256`: **SHA-256 канонической сериализации собственных полей без самого поля хэша**. Это контроль воспроизводимости, **не цифровая подпись и не защита от подделки**. Данные API и метаданные asset digest не являются результатом скачивания и побайтной проверки asset; поле `asset_content_verification=NOT_PERFORMED` сохраняется независимо от наличия digest.

**Всегда:** `application_release_readiness=NOT_VERIFIED`. Даже опубликованный GitHub Release исходников не означает подтверждённый выпуск исполняемого приложения.

## Проверка фактических байтов — T09.06

См. [RELEASE_ASSETS](RELEASE_ASSETS.md). Дополнительный флаг `--verify-assets` разрешает скачать прикреплённые файлы опубликованного Release и независимо подсчитать размер и SHA-256 байтов по метаданным GitHub. Режим **не включён по умолчанию**, требует `--verify-publication`, ограничен размером и доверенными HTTPS-хостами. `asset_content_verification=PASS` не означает доказательство происхождения сборки. Если опубликованных файлов нет, результат `NO_RELEASE_ASSETS`, а не PASS.

## Аттестация сборки — T09.07

[RELEASE_PROVENANCE](RELEASE_PROVENANCE.md) требует реально опубликованный GitHub Release с asset и отдельно проверяет связанную с ним GitHub attestation через официальный CLI. Самостоятельно создание релиза, его файлов, аттестаций или подписи не выполняется. Реальная эксплуатационная приёмка остаётся NOT_VERIFIED до появления такого выпуска.

## Безопасность, границы, дальнейшие этапы

- Никаких Git-записей, создания тегов, GitHub Release, загрузки артефактов и автоматического доступа к API.
- Запросы GitHub выполняются только по явным флагам, без обязательного платного API и без записи токенов в свидетельство.
- Проверка подлинности Git remote осуществляется по каноническому адресу `github.com/owner/repository`; локальные bare Git и сторонние хосты не принимаются за GitHub.
- Реальный GitHub Release для TESSERA пока **не** создан, и автоматическое его создание не входит в данный этап. Модульные положительные и отрицательные сценарии используют тестовые metadata без публикации.
- Дальнейшие задачи: проверка bytes/hash скачиваемых assets, независимая криптографическая подпись/аттестация, воспроизводимость сборки и управление конкурирующими релизами.

**Статус:** T09.05 — реализация и модульная проверка; эксплуатационная проверка на настоящем опубликованном GitHub Release — `NOT_VERIFIED`. Весь T09 остаётся `PARTIAL`.
