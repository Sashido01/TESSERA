# T09.06 — независимая проверка байтов GitHub Release assets

[**Русский — оригинал**](RELEASE_ASSETS.md) | [English — перевод](RELEASE_ASSETS.en.md)

## Назначение

`core/release_assets.py` скачивает **только по явному разрешению** asset опубликованного публичного GitHub Release и потоково сравнивает фактический размер и SHA-256 с метаданными GitHub REST API. Результат не зависит от субъективного ответа AI-агента. Никакие файлы не записываются на диск и никакие теги не изменяются.

**Важно:** метаданные размера и поля `digest` получены от того же GitHub, что и asset. Их совпадение с реально скачанными байтами доказывает целостность передачи относительно полученных метаданных, но **не независимую подпись разработчика, происхождение исходников, воспроизводимость сборки и не отсутствие вредоносного кода**.

## Использование

```bash
# Только локальная проверка Git и плана, без сети и скачиваний
python core/release_report.py --repo . --version 0.0.12

# Проверка метаданных публикации (без скачивания байтов)
python core/release_report.py --repo . --version 0.0.12 \
  --verify-publication --github-repo owner/repository

# Действительная проверка байтов (требует опубликованный Release с прикреплёнными assets)
python core/release_report.py --repo . --version 0.0.12 \
  --verify-publication --verify-assets --github-repo owner/repository \
  --format certificate

# Более крупный файл, только при обоснованной необходимости: лимит в байтах
python core/release_report.py --repo . --version 0.0.12 \
  --verify-publication --verify-assets --github-repo owner/repository \
  --max-asset-bytes 134217728
```

`owner/repository`, версия и пути — примеры, не реальные данные какой-либо пользовательской машины. Сначала проверь доверенный Git remote и выбранную публикацию. `--verify-assets` без `--verify-publication` запрещён. Для публикации и CI с полным набором доказательств отдельно включай `--verify-remote` и `--verify-ci --run-id <id>` **после завершения** GitHub Actions.

## Подтверждаемые условия

1. Публикация должна существовать, быть не draft и не prerelease, а выбранный Git remote должен соответствовать указанному GitHub-репозиторию.
2. Выбирается только URL вида `https://github.com/{owner}/{repo}/releases/download/{tag}/{filename}` с проверенными компонентами имени. HTTPS-переадресации разрешены исключительно на заранее известные домены GitHub CDN: `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`. Неизвестный хост, HTTP, подставленные credentials или не тот тег блокируются.
3. Для каждого asset нужен реальный `state=uploaded`, положительный размер и `digest=sha256:<64 hex>`. Если digest не опубликован, вместо предположений возвращается BLOCKED.
4. Поток читается кусками 64 КиБ, в памяти хранится только хэш и небольшой фрагмент. Проверяется фактическое число байтов, предел размера и итоговый SHA-256.
5. По умолчанию разрешено не более 64 МиБ на asset; верхний ограничитель 512 МиБ на asset. В одном запуске допускается не более 20 assets. Первое несовпадение останавливает дальнейшую проверку.
6. Ошибка сети, повреждение, незавершённая загрузка, превышение размера или неправильный SHA переводят `asset_content_verification` в BLOCKED.

При отсутствии asset-файлов возвращается **`NO_RELEASE_ASSETS`**, не PASS. Архивы исходников, автоматически предоставляемые GitHub, не являются прикреплёнными release assets и этим модулем не проверяются.

## Свидетельство

Отчёт и `--format certificate` содержат `publication_asset_content_verification`, `verified_assets` с фактическим SHA-256 и количеством байтов, `artifact_provenance=NOT_VERIFIED` и `application_release_readiness=NOT_VERIFIED`.

Только при совпадении байтов хотя бы одного asset, подтверждённом опубликованном GitHub Release, точном аннотированном remote-теге и успешном завершённом CI свидетельство может получить состояние **`SOURCE_ASSETS_BYTES_VERIFIED`**. Это означает **целостность загруженных байтов относительно метаданных GitHub**. Никаких состояний `RELEASED` для приложения модуль не присваивает.

Контрольная сумма `evidence_sha256` относится к **самому JSON-свидетельству**, не подписана и не препятствует умышленной подделке свидетельства.

## Связь с криптографической attestation — T09.07

Сравнение скачанных байтов с GitHub digest ещё не доказывает происхождение файла. [RELEASE_PROVENANCE](RELEASE_PROVENANCE.md) добавляет явную проверку GitHub Sigstore/SLSA attestation **для локально сохранённого пользователем файла**. Прежняя потоковая проверка T09.06 не записывает файлы; T09.07 независимо хэширует уже имеющийся локальный asset и связывает его с подписанным workflow. Не выдавать соответствие одного digest за криптографическую подпись.

## Испытания и реальные границы

Сценарии проверяют корректные и повреждённые байты, усечённый и слишком длинный ответ, отсутствие digest, ошибки URL/redirect, лимиты размера, повторяющиеся имена, отсутствие assets и блокирование неподтверждённой публикации. В тестах содержимое имитируется локальными потоками; **платная инфраструктура, внешние скачивания и изменение настоящих тегов не требуются**.

На момент подготовки этапа у TESSERA отсутствует реальный опубликованный GitHub Release с прикреплёнными файлами. Поэтому **живой end-to-end download на проекте пока NOT_VERIFIED**. Полный T09 остаётся PARTIAL: нужна независимая аттестация происхождения, безопасное управление конкурентными релизами и доказательство работоспособности исполняемых продуктов.

Источник формата asset metadata: [официальная GitHub REST API документация](https://docs.github.com/en/rest/releases/assets).
