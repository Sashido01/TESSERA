# T09.04 — независимая проверка завершённого GitHub Actions

[**Русский — оригинал**](RELEASE_CI.md) | [English — перевод](RELEASE_CI.en.md)

## Назначение

Новый компонент `core/release_ci.py` проверяет **фактические данные GitHub Actions API** и не принимает слова агента о прохождении тестов за доказательства. Он предназначен для **уже завершённого** запуска workflow. Второй компонент `core/release_state.py` формирует ограниченное состояние на основе проверенных фактов, не объявляя готовым или опубликованным приложение.

Интеграция в [Release Report](RELEASE_REPORT.md) включается **только по явному флагу** `--verify-ci`. Без него отчёт остаётся локальным. При проверке требуется указывать доверенный GitHub-репозиторий, идентификатор завершённого workflow run и локальный проект с полным SHA проверяемого коммита.

## Пример команды

После полного завершения GitHub Actions:

```bash
python core/release_report.py --repo . --version 0.0.10 \
  --verify-ci --github-repo owner/repository --run-id 123456789

# Дополнительно проверить удалённый тег в том же отчёте
python core/release_report.py --repo . --version 0.0.10 \
  --verify-remote --verify-ci --github-repo owner/repository --run-id 123456789
```

Команды выше — **синтаксические примеры**, а не сведения о конкретном workflow run. Укажи фактические реквизиты доверенного репозитория и завершённого запуска. Запуск требует действительного локального аннотированного тега `v0.0.10`. Путь пользователя в публичных документах не записывается.

## Что сравнивается с GitHub

Через официальные REST endpoint `GET /repos/{owner}/{repo}/actions/runs/{run_id}` и `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs?per_page=100` проверяются:

1. Действительный ID workflow run, точное имя репозитория и полный SHA целевого коммита.
2. `event=push`, `head_branch=main` и ожидаемый файл workflow `.github/workflows/validate.yml`.
3. `status=completed` и `conclusion=success` у всего запуска.
4. Реальный `run_attempt` у workflow и у обеих обязательных jobs.
5. Успешное завершение **обеих** jobs: `validate` и `Создать аннотированный тег проверенной версии`.
6. Полноту списка jobs: `total_count` должен совпадать с числом полученных элементов. Если jobs больше одного запрошенного API-окна (100), проверка блокируется, а не молча игнорирует часть проверок.

Отсутствующая или пропущенная job, другой SHA, другой workflow, незавершённый запуск, несовпадающий номер попытки, сетевая ошибка и недоступный API дают `ci_status=BLOCKED`, а не PASS.

## Что означает результат

В отчёт добавлены `ci_status`, `ci_run_id`, `ci_repository`, `ci_observed_commit_sha` и `ci_run_attempt`. Чистая функция `core/release_state.py` возвращает состояния `CI_VERIFIED` или `CI_AND_REMOTE_TAG_VERIFIED` только при положительных проверках.

**Важное ограничение:** поле `release_readiness` остаётся `NOT_VERIFIED` во всех состояниях T09.04. Успех workflow подтверждает выполнение зарегистрированных GitHub jobs; он не доказывает достаточность тестов, подлинность созданных бинарников, доставку приложения пользователю, GitHub Release или отсутствие уязвимостей.

## Почему проверка не встроена в текущий job публикации тега

Нельзя надёжно проверить состояние `completed/success` того же самого workflow **пока он ещё исполняется**. Это образовало бы круговую зависимость.

Поэтому `tag_microversion` продолжает подтверждать локальный и удалённый аннотированный тег после его отправки, а T09.04 отдельно проверяет **завершённый** run по запросу оператора или независимого внешнего контроллера. Автоматизация такой последующей проверки и хранение неизменяемых свидетельств будут отдельным этапом — нельзя изображать их выполненными.

## Безопасность и ограничения

- Запрос к GitHub выполняется только при `--verify-ci`; используется HTTPS и фиксированный `api.github.com`. Внешние произвольные URL не принимаются.
- В инструменте нет Git-записи, `git push`, токенов, пользовательских команд, автоматического запуска тестов или публикации.
- Применяются ограничение 15 секунд на запрос и 2 МиБ на JSON-ответ. Текст сетевых исключений, токены и заголовки ответа не публикуются в итоговом отчёте.
- Публичные GitHub Actions данные доступны без обязательного токена в пределах лимитов публичного API. Для приватных репозиториев эта версия не предусматривает авторизованный режим; это отдельное ограничение.
- Доверенное значение `--github-repo` вводится явно; приложение не доказывает независимо, что выбранный пользователем репозиторий соответствует локальному `origin`.
- Достоверность основана на GitHub REST API и HTTPS, но не на криптографической аттестации артефактов.
- Сетевые сценарии тестируются через контролируемые подмены HTTP, без вызовов внешнего API; интеграцию на реально завершённом workflow необходимо подтвердить отдельно.
