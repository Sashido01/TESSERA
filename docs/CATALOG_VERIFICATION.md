# T09.09 — независимая офлайн-проверка ZIP-каталога

[**Русский — оригинал**](CATALOG_VERIFICATION.md) | [English — перевод](CATALOG_VERIFICATION.en.md)

## Назначение

`tools/verify_catalog_package.py` проверяет фактические байты уже скачанного ZIP каталога TESSERA. Сеть, токены, GitHub CLI, извлечение архива и исполнение кода не нужны. Параметры `--version` и `--source-commit` должны поступать из независимо проверенного источника, а не из недоверенного манифеста.

~~~bash
python tools/verify_catalog_package.py \
  --archive TESSERA-catalog-v0.0.15.zip \
  --version 0.0.15 \
  --source-commit <полный-SHA-релизного-коммита>
~~~

Команда — пример после получения действительного файла. Реальный signing run и GitHub Release в этом этапе не подтверждены. Сначала нужно независимо установить точный remote-тег и SHA коммита.

## Проверки

- Обычный файл, не symlink, размер ZIP до 64 МиБ.
- Каждая запись находится под точным префиксом `TESSERA-X.Y.Z/`. Запрещены обход `..`, абсолютные пути, обратные слэши, повторения, symlink, каталоги, шифрование и сжатие.
- Не более 2048 записей, 4 МиБ на файл и 1 МиБ на манифест. Распаковка на диск не выполняется.
- `MANIFEST.json` обязан содержать поддерживаемую схему, версию и переданный извне полный SHA коммита. Его набор файлов должен точно совпадать с записями ZIP.
- Для каждого файла сверяются фактические размер и SHA-256. Обязательны LICENSE, оба README, VERSION и хотя бы один `skills/<имя>/SKILL.md`.
- Успешный отчёт содержит SHA-256 ZIP, количество файлов, `status=PASS`, `attestation=NOT_VERIFIED` и `publication=NOT_VERIFIED`.

Любая ошибка даёт `BLOCKED` и код завершения 1; абсолютные локальные пути, содержимое файлов и секреты в отчёт не попадают. Это проверка внутренней согласованности содержимого **относительно манифеста**, а не подлинности автора: злоумышленник может изменить одновременно ZIP и манифест.

## Отдельное доказательство происхождения

Для заявления о подлинности отдельно подтвердите аннотированный `vX.Y.Z`, полный SHA коммита и проверенную `gh attestation verify` с точными `--repo`, `--source-ref`, `--source-digest`, `--signer-workflow` и запретом self-hosted runners. Существующий `core/release_provenance.py` связывает подпись с **опубликованным GitHub Release asset** и его метаданными. Временный GitHub Actions Artifact — другой канал распространения и пока не подключён к этому контракту.

**Нельзя** на основании одного `status=PASS` заявлять SIGNED, PUBLISHED, RELEASED или готовность приложений, использующих навыки. Работу в реальных Codex/Harness/Claude/Hermes этот скрипт тоже не доказывает.

**Безопасность CLI:** для реального `gh attestation verify` и `gh run download` используйте `gh 2.102.0+`. Более ранние версии содержали опубликованные ошибки проверки signer/ref и загрузки через symlink. См. [RELEASE_PROVENANCE](RELEASE_PROVENANCE.md).

## Приёмка

Положительный тест строит архив существующим упаковщиком; отрицательные охватывают подмену байтов, чужую версию/SHA, битый архив, отсутствие манифеста, duplicate, traversal, абсолютный путь, symlink и сжатие. T09 остаётся PARTIAL до живой подписанной сборки, независимой проверки и остальных требований Release Core.

## Инструменты обновления в исходном ZIP (кандидат 0.0.97)

С 0.0.97 ZIP-контракт требует CATALOG.json, UPDATE RU/EN, профильную инструкцию RU/EN и три read-only инструмента UP01/UP02. Проверка отклоняет отсутствующие/лишние файлы и несогласованные версии каталога даже при пересчитанном манифесте. Старые ZIP проверяются по прежнему контракту. ZIP остаётся runtime subset: тесты навыков исключены, поэтому это не raw Git tree и не staging для skill_tree.py. Проверяющий код брать из независимо доверенного checkout; не выполнять код из непроверенного ZIP. Аттестация, live resolver, gh metadata, apply и rollback отдельно открыты.
