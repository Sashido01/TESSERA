# Архитектура TESSERA

[**Русский — оригинал**](ARCHITECTURE.md) | [English — перевод](ARCHITECTURE.en.md)

## Основной принцип

Один публичный репозиторий, множество самостоятельных навыков. Каждый навык живёт в `skills/<slug>/`, имеет точку входа `SKILL.md`, собственные инструкции, примеры и, при необходимости, читающие или изменяющие данные скрипты.

## Уровни системы

1. **Каталог** — README, правила участия, безопасность, общие тесты.
2. **Навыки** — переносимые инструкции и сопутствующие файлы без обязательного общего runtime.
3. **Интеграции** — будущие, отдельно проверяемые адаптеры для Harness, Codex и других систем.
4. **Проверки** — локальная команда и GitHub Actions; они проверяют структуру и тесты, но не гарантируют качество ответов модели.

## Межплатформенность навыков

Общая часть каждого навыка использует стандарт Agent Skills без обязательной зависимости от одного агентного рантайма. Codex, DeepSeek Harness, Claude Code и Hermes загружают стандартный `SKILL.md`, но имеют собственные правила обнаружения, доверия и хуков. Для первого навыка подготовлены инструкции и безопасный установщик; отсутствие фактических испытаний в конкретных клиентах обозначается `NOT_VERIFIED`. Обязательный тег релиза проверяется детерминированным Git-скриптом отдельно от решений модели.

## Утверждённое направление развития

Текущая структура `skills/<slug>/` сохраняется. [Дорожная карта](ROADMAP.md) предусматривает **одно независимое ядро Release Core** (версия, фактические проверки, Git/теги, доказательства) и **тонкие адаптеры** Codex, DeepSeek Harness, Claude Code, Hermes. Новые каталоги создаются только при реальной реализации, не в качестве пустых заготовок.

Основной **планируемый** канал распространения — официальный GitHub CLI `gh skill`, после практической проверки и фиксации совместимой версии. Существующий Python-установщик остаётся минимальным решением для офлайн-работы и нестандартных профилей.

Для CI предлагается официальный `skills-ref` как эталонная проверка формата; собственные проверки TESSERA сохраняют специальные правила микроверсий и релизов. NVIDIA SkillEvaluator **только Tier 1**, после изолированной проверки бесплатной работы и ресурсов. Tier 2/3 и обязательные платные AI API исключены. Все условия: [DEPENDENCIES.md](DEPENDENCIES.md). Это целевая архитектура, а не утверждение о завершённой интеграции.

## Начало независимого Release Core

Первый компонент T09.01 — [инспектор Git-доказательств](RELEASE_CORE.md). Он читает версию и проверяет аннотированный тег точного коммита, в том числе исторического. Проверка **не** запускает сборки, не выполняет `git push` и не обещает состояние RELEASED. Сохранён независимый от агента контракт JSON для будущих адаптеров.

## Проверка завершённого CI (T09.04)

В [документе Release CI](RELEASE_CI.md) описано независимое чтение GitHub Actions API для уже завершённого запуска, без автоматического доступа к сети. Чистое ядро состояний учитывает только запрошенные и реально подтверждённые доказательства; оно **не** присваивает статус RELEASED. Проверка того же workflow до его завершения запрещена во избежание циклической зависимости.

## Публикация исходников и свидетельство T09.05

[Документ RELEASE_PUBLICATION](RELEASE_PUBLICATION.md) описывает отдельную проверку metadata опубликованного GitHub Release и воспроизводимое неподписанное свидетельство. Наличие тега и успешного CI не доказывают GitHub Release, а GitHub Release не доказывает подлинность скачанных артефактов. Все запросы API включаются только явно, доступ к Git ограничивается чтением. Ни один модуль не публикует релизы самостоятельно.

## Независимая проверка байтов T09.06

[RELEASE_ASSETS](RELEASE_ASSETS.md) описывает потоковое чтение действительных файлов опубликованного GitHub Release и сверку размера/SHA-256 с его API-метаданными. Загрузка допускается только с `--verify-assets` и `--verify-publication`. Сетевые redirect ограничены известными GitHub CDN; файловые операции и установка приложения не выполняются. Подтверждение байтов не доказывает происхождение сборки или готовность ПО.

## Криптографическое подтверждение происхождения — T09.07

[RELEASE_PROVENANCE](RELEASE_PROVENANCE.md) использует **официальный GitHub CLI** для проверки Sigstore/SLSA attestation конкретного локального артефакта, связанной с исходным SHA, релизным тегом и доверенным workflow. Сетевые действия выполняются лишь с явным `--verify-provenance`. Само JSON-свидетельство Release Core остаётся неподписанным; доказательства безопасности и работоспособности ПО не формируются.

## Детерминированный пакет и доверенная сборка — T09.08

[TRUSTED_BUILD](TRUSTED_BUILD.md) фиксирует действительный исходный ZIP каталога с манифестом SHA-256 и точным коммитом. Подписывающий GitHub Actions workflow запускается вручную **после** публикации аннотированного тега и не выполняется в PR. Для TESSERA это исходный пакет Agent Skills, не бинарное приложение. Новый [порядок работы с ветками](BRANCHING.md) не требует ветки на каждый промежуточный коммит.

## Установка

Для каждой агентной системы определите реально активный каталог навыков. Копируйте весь каталог навыка. При необходимости создавайте symlink/junction только после проверки поддержки агентом и безопасности пути. Не приравнивайте наличие файла к автоматическому применению навыка.

## Публикация

Git-коммит, аннотированный тег, GitHub Release и готовый сборочный артефакт — разные состояния. Каждый из них должен подтверждаться отдельно.

## Переносимость

Пути к рабочим каталогам задаются в окружении пользователя и не должны быть зашиты в публичные инструкции, конфигурацию и исполняемые скрипты.
