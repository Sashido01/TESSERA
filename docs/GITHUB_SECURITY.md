# Защита GitHub-репозитория TESSERA

[**Русский — оригинал**](GITHUB_SECURITY.md) | [English — перевод](GITHUB_SECURITY.en.md)

## Подтверждённое состояние на 23.11.2026

Через GitHub API подтверждены два активных Rulesets: `Protect main` (ID `27932550`) для основной ветки и `release tags` (ID `27932769`) для тегов `v*`.

Для `main` включены: Pull Request с 0 обязательных одобрений, проверка `validate` от GitHub Actions, обязательная актуальность ветки, линейная история, запрет удаления и принудительного обновления. Для `v*` запрещены обновление, удаление и force-push; создание новых тегов не запрещено. Bypass list пуст.

**Отрицательная приёмка подтверждена:** тестовый Pull Request #1 с неверным `VERSION=0.0.99` при текущей `0.0.5` дал FAIL в `validate`, тегирование не запускалось. [Запуск CI](https://github.com/Sashido01/TESSERA/actions/runs/45255895372).

**Положительная приёмка подтверждена:** исправленный Pull Request #1 прошёл [проверку validate](https://github.com/Sashido01/TESSERA/actions/runs/45256267316), был объединён методом Squash and merge в коммит `f2d961bdb0a0e768c9663a374e299d3e42ee409b`; после слияния [GitHub Actions](https://github.com/Sashido01/TESSERA/actions/runs/45256377248) создал аннотированный тег `v0.0.6` (объект `1eeff57da476ef7a8930664ef6a494f586c00e79`), который указывает на тот же коммит.

**Остаётся NOT_VERIFIED:** практический отрицательный тест попытки изменения/удаления уже опубликованного тега, проверка административного обхода и прямого push. Эти опасные действия не проводились над рабочей историей; T08 сохраняет статус PARTIAL до безопасной полной приёмки.

## Реализованные ограничения workflow

- У `validate` минимальное право `contents: read`, без сохранения Git-учётных данных после checkout.
- `tag_microversion` — отдельная задача с `contents: write` после успешной проверки; только push в `main`.
- Официальные `actions/checkout` и `actions/setup-python` закреплены полными проверенными SHA.
- Перед созданием и отправкой тега проверяется совпадение удалённого HEAD `main` с успешно проверенным коммитом.
- При сбое сетевой проверки существующего тега операция останавливается, а не предполагает отсутствие тега.
- Проверяются тип аннотированного тега, текст аннотации, точный SHA коммита и SHA тега на remote.
- `tools/check_workflow_security.py` проверяет эти требования статически.

**Ограничение:** это защита от ряда ошибок, не полноценная блокировка конкурирующих релизов. Между проверкой SHA и push сохраняется окно гонки; независимая координация предусмотрена T15.

## Действующие настройки и инструкция для повторной проверки

Ниже сохранена процедура настройки на случай восстановления или аудита. Правила уже активированы владельцем; менять их без отдельной причины не требуется.

## Включение защиты ветки

В GitHub: `Settings → Rules → Rulesets → New ruleset → New branch ruleset` (названия элементов могут меняться).

1. Создать `TESSERA main protection`, выбрать ветку `main`.
2. Запретить удаление ветки и принудительное обновление истории.
3. Требовать Pull Request перед слиянием: после активации прямой процесс внесения коммитов нужно заменить работой через PR.
4. Назначить обязательную проверку `validate` с проверкой доверенного источника GitHub Actions.
5. Ограничить исключения для администраторов; не настраивать бесконтрольный обход.
6. Проверить на отдельной ветке или в режиме Evaluate, если он доступен, затем включить Active.

## Защита тегов

Отдельный Tag Ruleset для `v*` должен блокировать обновление и удаление ранее опубликованных тегов. Для будущих независимых навыков исследовать шаблоны `*/v*`.

**Создание нового тега должно остаться доступным задаче GitHub Actions после PASS**, иначе система выпуска перестанет работать. Не вводить общее исключение, которое позволяет перезаписывать существующие теги. Проверить безопасные исключения с временным тестовым префиксом.

## Упрощённый цикл веток и проверяемая подписывающая сборка

В [BRANCHING](BRANCHING.md) закреплено: **не создавать новую ветку для каждого коммита или исправления**. Одна короткоживущая ветка используется для связанных изменений и одного Pull Request. Тег создаётся только после CI и слияния в защищённую `main`. В T09.08 появился отдельный [TRUSTED_BUILD](TRUSTED_BUILD.md): signing workflow запускается исключительно вручную по тегу, не имеет права Git-записи и не подписывает код из PR. Статический checker проверяет pinned actions и ограничения permissions.

## Приёмка T08

- Rulesets реально активны, соответствуют ветке `main` и тегам.
- Неудачные изменения версии или перевода блокируют обязательный CI для PR.
- Неразрешённая запись и принудительное изменение истории отклоняются.
- Проверенный workflow способен создать новый аннотированный тег и не способен переписать существующий.
- Проверены права GitHub Actions и режим работы администраторов.
- Недоступные испытания отмечены `NOT_VERIFIED`. Не проводить разрушительные тесты на рабочей `main`.

## Границы

Настройки TESSERA не защищают автоматически репозитории, где установлен Microversion Release: потребителям также нужны собственные Git/CI-ограничения. Старая Git-история остаётся доступной после очистки актуальных документов.
