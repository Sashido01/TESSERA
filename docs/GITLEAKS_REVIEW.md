# T12.02.02.02 — проверка текстового снимка Gitleaks

[**Русский — оригинал**](GITLEAKS_REVIEW.md) | [English — перевод](GITLEAKS_REVIEW.en.md)

Используется официальный [Gitleaks v8.30.1](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1), MIT. Linux amd64 архив закреплён SHA-256 из metadata официального GitHub Release. Из архива извлекается только исполняемый файл. Не используются GitHub Action Gitleaks, платные услуги, AI API, Tier 2/3 или автоматические установщики NVIDIA.

## Область и защита

- Снимок всех отслеживаемых Git файлов рабочего дерева (в CI — checkout). Каждый непустой UTF-8 файл подаётся отдельно через stdin; пустые учитываются отдельно. Symlink, недопустимые пути, бинарные/не-UTF-8 файлы и превышение лимитов блокируют проверку. Git-история, неотслеживаемые файлы, бинарные и вложенные архивы не проверяются.
- [Upstream issue #2316](https://github.com/gitleaks/gitleaks/issues/2316) сообщает о пропуске текстовых файлов с архивоподобными именами. stdin не передаёт имя файла; проверяется точное число прочитанных байтов каждого файла. Правила, зависящие от имени файла, требуют отдельного исследования; используется встроенная конфигурация и её content allowlists.
- Отдельный временный каталог без конфигурации репозитория и наследуемых ключей; --ignore-gitleaks-allow, --redact=100, отдельный exit code 10 для находок. Не применяются пользовательские baseline, исключения или подавления.
- JSON и stderr захватываются в память, не печатаются и не публикуются как артефакты. Проверяются версия, коды завершения, объём прочитанных данных, отсутствие частичного сканирования, валидность JSON, редактирование поля Secret, неизменность снимка, положительный и отрицательный синтетические сценарии. В итоговом отчёте только агрегаты по кодам правил и группам tests/other.
- Синтетический маркер не является настоящим ключом, формируется только в памяти. Проверяется обнаружение даже с gitleaks:allow и отсутствие маркера в захваченном выводе. Это не доказательство обнаружения всех секретов или защиты произвольных полей отчёта; изоляция окружения не является сетевым sandbox.
- Находки advisory до ручного анализа; сбой выполнения или неполное покрытие блокируют CI. NO_FINDINGS относится только к указанной области и встроенным правилам.

## Достижимая Git-история (0.0.30)

Вторая независимая проверка, `python tools/check_gitleaks_history.py --repo . --cli <путь-к-gitleaks>`, инвентаризует объекты, достижимые из локальных refs и HEAD, без подмены Git-объектов; запрещает shallow, проверяет размеры уникальных blob и UTF-8, затем сканирует каждый непустой blob через stdin в ограниченном пуле процессов. Сверяется инвентарь до и после, число байтов и обнаружение синтетического маркера, удалённого в следующем коммите. Бинарные и неподдерживаемые кодировки блокируют проверку; отчёты только агрегированные. Проверяется содержимое, а не правила по именам, не полученные с remote refs, сообщения коммитов, недостижимые объекты или содержимое архивов. ## Правила, зависящие от пути

В upstream v8.30.1 пять правил с явным условием пути: PHP/Freemius, Terraform, Kubernetes YAML, NuGet config, имена PKCS#12. Отдельная проверка перечисляет подходящие пути текущего дерева и уникальные пары (правило, blob) из всех достижимых деревьев коммитов. Каждый кандидат сканируется под каноническим именем, сохраняющим условие правила; проверяется точное байтовое покрытие, используется только целевое правило и синтетическое обнаружение каждого из пяти правил. Это обход ошибки архивоподобных имён, но не полное воспроизведение всех allowlist по путям. Исходные имена и сырые находки не выводятся. Недостижимые объекты и не полученные remote refs не проверяются. [CI 45369335974](https://github.com/Sashido01/TESSERA/actions/runs/45369335974) PASS: 443+19 тестов; 598 уникальных UTF-8 blob, 5639755 байт, 0 находок; пять синтетических правил PASS; 4 текущих YAML-файла, 28 исторических пар правило/blob из 37 коммитов, 0 находок. Это ограниченная проверка побочных эффектов, не мониторинг системных вызовов, не гарантия отсутствия внешних/временных записей и не sandbox. Лимит вывода проверяется после захвата, не является жёстким лимитом памяти. Archives Identify вызывается до проверки глубины: отключение обхода архивов не доказывает недостижимость всех зависимостей. ## TD04 — пакетное чтение Git-объектов (черновой кандидат)

Host review читает до 32 объектов / 4 MiB ожидаемого содержимого одним git cat-file --batch, сверяет точный заголовок, порядок, framing, размер, OID, UTF-8 и конец потока. Сканы по-прежнему отдельные, 4 workers, полный inventory/recheck и deadline. Container parity сохраняет прежнее независимое чтение по одному объекту. Постзахватный предел не является жёстким ограничением памяти subprocess. Прототип парсера и реального batch Git 10/10 Linux PASS; не полный suite кандидата. Новые регрессии включают SHA-256, перестановку, повреждённый заголовок/фрейм/байты, binary/encoding, размер/число и живой Git. Реальный CI, нативная Windows-проверка и измерение полного history job обязательны; скорость CI NOT_VERIFIED. Версия не назначается до освобождения интеграционного слота.

## TD04 — сверка перед интеграцией и дальнейшие границы (26.11.2026)

Сверены четыре изменённых пути с точным main v0.0.84 `df8116f35fdfe2ccb7ee4a4316053455c407d3e9`: 4/4 Git blob исходной базы v0.0.81 совпадают с main, кандидат не перезаписывает новые версии этих файлов. Версию назначить после приёмки текущего PR #92 и повторной сверки. Полный suite и живой Gitleaks всё ещё требуются. Snapshot SHA-256 относится к карте уникальных blob OID/размеров, а не к полному снимку refs: смена refs при неизменном наборе blob не обязательно обнаруживается; это проверка покрытия содержимого, не транзакционная фиксация истории. Для следующего усиления отдельно оценить хэш упорядоченных refs/HEAD и две сверки; не переносить PASS на другое состояние или другой scanner/config. [Git cat-file](https://git-scm.com/docs/git-cat-file): --batch-command --buffer/flush допускают постоянный процесс и сокращение flush, но требуют независимого протокола с контролем дедлайна/EOF/памяти; для первого релиза сохранить более простой bounded batch, измерить реальный CI. [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency): отмена устаревших PR runs может экономить минуты, но не должна отменять main/tag/build-attested runs или подменять проверку точного head. Отдельно оценить workflow-level PR-only group и cancel-in-progress, тесты политики и разрешения на изменение workflow; в этом кандидате workflow не меняется. Старые завершённые runs сохранять как evidence.
