# Непрерывная параллельная разработка TESSERA

[**Русский — оригинал**](PARALLEL_WORKFLOW.md) | [English — перевод](PARALLEL_WORKFLOW.en.md)

## Решение владельца от 25.11.2026

Скорость работы на GitHub — самостоятельное требование. Нативные решения GitHub предпочтительны; излишняя сложность, внешние обязательные сервисы и платные API не допускаются. Все навыки должны работать локально без GitHub. Третий навык Repository Workflow утверждён; остальные новые навыки не добавлять без решения владельца. Не прекращай независимую работу при CI/блокировке одного потока.

## Практический цикл
1. Сверить main, точный тег, все активные PR/CI и существующие рабочие ветки. Обновить реестр [технического долга](TECHNICAL_DEBT.md).
2. Обработать завершившиеся проверки, устранить конкретный сбой той же ветки. Один слот интеграции общего VERSION/CHANGELOG; не назначать следующую общую версию до освобождения слота. Черновые ветки без нового корневого VERSION допустимы; не направлять их в обязательный релизный CI до подготовки кандидата.
3. Поток 0 — инфраструктура; далее Microversion Release, Project Audit, Repository Workflow; новые утверждённые навыки в порядке каталога. Проверить каждый поток, выполнять независимые задачи с непересекающейся областью записи/ресурсами. Сохранять незавершённую работу. Если все заняты, исследовать открытый вопрос из roadmap/долга, а не добавлять сканеры ради количества.
4. Привязать проверку к точному SHA, актуальной базе и прежнему подтверждённому тегу; squash только после всех обязательных проверок; подтверждать main CI и тег до следующего принятия. Слияние не равнозначно релизу. Не удалять рабочую ветку до доказанного сохранения результата.
5. Фиксировать изменения и блокеры; GitHub Actions продолжает уже запущенный CI независимо. Без работающего исполнителя между сессиями код не развивается автоматически.

## Ускорение
Фактический baseline validate: main 45568501762 — 943 с, включая 488 с две проверки истории Gitleaks; PR 45569400436 — 700 с, включая 345 с история. Источники: API jobs, времена окончания минус начала. Доли 51,7% и 49,3%. Цель первого этапа — независимый history job (host + Docker parity остаются вместе), остальные проверки в другом job, итоговый обязательный validate при успехе обеих групп. Сохранить pinned Actions, read-only, полный охват и tag gate. Доказать отказ при skipped/cancelled/failure, проверить отрицательные сценарии, повторить CI на сравнимых снимках. Не объявлять ускорение по расчётной оценке. Далее: измерение очереди, p50/p95 и runner-minutes; быстрая локальная проверка, затронутые тесты для обратной связи, кеш проверенных артефактов только после аудита. Снижение полного критического пути и времени до первой ошибки важнее количества jobs.

## Нативный GitHub
Личный публичный репозиторий не поддерживает организационную Merge Queue; перенос не нужен. Используй один координатор и проверку ожидаемого HEAD (gh pr merge --match-head-commit), действующие Rulesets, строгий required check и автоматическое удаление принятых веток. Issues с зависимостями — при необходимости для активных задач; существующая roadmap остаётся каноническим реестром этапов. Не дублируй задачи и не закрывай их ради нулевого счётчика. GitHub Projects опционален. Concurrency — только для подходящих групп CI, никогда не отменять незавершённый уникальный выпуск. Нативные шаблоны и reusable workflows предпочтительны при доказанной пользе. Настройки Rulesets/тегов требуют отдельной согласованной операции.

## Профили локальных проектов
Git без remote, локальные ветки/worktrees, штатные тесты, VERSION/CHANGELOG по правилам выбранного проекта, локальный журнал задач и теги. Не добавлять GitHub, внешние сервисы, telemetry или обязательные зависимости. Интеграция Codex/Harness проверяется в реальном окружении.
