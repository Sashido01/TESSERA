# Публикация первого Immutable Release (0.1.0)

[**Русский — оригинал**](IMMUTABLE_RELEASE.md) | [English — перевод](IMMUTABLE_RELEASE.en.md)

Решение владельца принято 26.11.2026. Не выполнять публикацию до закрытия G01–G12 в применимой последовательности: до создания тега обязательны предрелизная приёмка и проверенные исходники, после тега — exact main CI, сборка/проверка ZIP, draft, публикация и независимая проверка. Нельзя заявить RELEASED до финального подтверждения. Текущий статус плана NOT_RUN.

1. В Settings → General → Releases включить Enable release immutability. Из доверенного терминала владельца проверить `gh api --include repos/Sashido01/TESSERA/immutable-releases`: успешный HTTP 204 подтверждает включение. 404, ошибка прав/сети или недоступный endpoint не подтверждают включение. Не ослаблять действующие Rulesets. [Настройка](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes).
2. После подтверждённых exact v0.1.0 и main CI запустить `gh workflow run build-attested-catalog.yml --repo Sashido01/TESSERA --ref v0.1.0`. Найти конкретный run по workflow_dispatch, tag, SHA, attempt, успеху. Скачать его конкретный artifact `tessera-catalog-v0.1.0` в новую приватную пустую папку. Проверить manifest и размер ZIP, SHA-256, воспроизводимость по [Trusted Build](TRUSTED_BUILD.md).
3. Выполнить `gh attestation verify <zip> --repo Sashido01/TESSERA --source-ref refs/tags/v0.1.0 --source-digest <exact-commit> --signer-workflow Sashido01/TESSERA/.github/workflows/build-attested-catalog.yml --deny-self-hosted-runners`. Записать реальный результат и digest. Не использовать placeholder как фактический SHA. Проверить отсутствие существующего Release по этому тегу. Если существует — остановиться, изучить фактическое состояние, ничего не перезаписывать.
4. Создать только draft из уже существующего тега: `gh release create v0.1.0 <verified-zip> --repo Sashido01/TESSERA --verify-tag --draft --title "TESSERA 0.1.0" --notes-file <reviewed-bilingual-notes>`. Прикрепить все утверждённые файлы до публикации; не использовать --clobber. Проверить tagName, isDraft, exact assets, размеры и скачанные байты из draft в новую папку. Сверить SHA-256 с проверенным ZIP и повторить attestation verify. Проверить настройки immutability повторно. Не публиковать, если хотя бы один обязательный результат отсутствует.
5. Только после успешной независимой проверки draft и подтверждённой готовности опубликовать через `gh release edit v0.1.0 --repo Sashido01/TESSERA --draft=false`. После публикации проверить `gh release verify v0.1.0 --repo Sashido01/TESSERA` и `gh release verify-asset v0.1.0 <zip> --repo Sashido01/TESSERA`; скачать опубликованный ZIP и повторить SHA-256 / workflow attestation. Проверить опубликованный Release, immutable=true в metadata, точный Git tag и CI. GitHub Release attestation и Actions workflow attestation — различные свидетельства. Динамические Source code ZIP/TAR не проверяются verify-asset. Не пытаться изменять immutable assets/tag, при дефекте — новая версия по политике.

Документация команд: [gh release create](https://cli.github.com/manual/gh_release_create), [gh release verify](https://cli.github.com/manual/gh_release_verify), [gh release verify-asset](https://cli.github.com/manual/gh_release_verify-asset), [gh attestation verify](https://cli.github.com/manual/gh_attestation_verify). Конкретные действия выполняются владельцем/авторизованным release operator; текущий коннектор не поддерживает dispatch и публикацию Release. Это runbook, не свидетельство выполнения.
