# Release Preflight — проверка готовности перед тегированием (T09.02)

[**Русский — оригинал**](RELEASE_PREFLIGHT.md) | [English — перевод](RELEASE_PREFLIGHT.en.md)

## Назначение

`core/release_preflight.py` проверяет, что версия и записи релизных изменений присутствуют **в конкретном Git-коммите**, а команды обязательных тестов и сборок явно описаны в `release-checks.json` целевого проекта.

**По умолчанию используется безопасный `--plan`: никакие пользовательские команды не запускаются.** Только явный `--execute` запускает утверждённые команды целевого проекта. Это необходимо учитывать при подключении навыка к агентам: автоматически исполнять команды из недоверенного Pull Request запрещено.

## Два режима

```bash
# Только чтение конфигурации, VERSION, CHANGELOG и состояния Git.
python core/release_preflight.py --repo <project-root> --version 0.0.8 --plan

# Запуск утверждённых проверок в доверенном проекте.
python core/release_preflight.py --repo <project-root> --version 0.0.8 --execute --expected-commit <full-commit-sha>
```

В `--plan`: `stage=PREPARED`, `checks_status=NOT_RUN`, если предварительная проверка прошла. В `--execute`: после успешного выполнения всех объявленных проверок — `stage=VALIDATED`, `checks_status=PASS`. При неудаче — `stage=BLOCKED`. **Ни один из этих режимов не присваивает статус RELEASED** и не утверждает, что Git-тег или публикация уже состоялись.

## Формат конфигурации

Пример для программы, где есть отдельная сборка:

```json
{
  "schema_version": 1,
  "version_file": "VERSION",
  "release_notes": ["CHANGELOG.md"],
  "build": [
    {
      "id": "package-build",
      "argv": ["python", "-m", "build"],
      "cwd": ".",
      "timeout_seconds": 300
    }
  ],
  "tests": [
    {
      "id": "unit-tests",
      "argv": ["python", "-m", "unittest", "discover", "-s", "tests"],
      "cwd": ".",
      "timeout_seconds": 300
    }
  ]
}
```

Это пример схемы, а не утверждение, что `python -m build` доступен или подходит каждому проекту. Для программ без отдельной сборки вместо массива `build` допускается **явное** `{"not_applicable_reason": "..." }` с содержательным объяснением. Обязательных `tests` должно быть не меньше одного. Текущая TESSERA содержит свой [release-checks.json](../release-checks.json), в котором отсутствие отдельного артефакта сборки объяснено, а две группы тестов перечислены отдельно.

## Проверки безопасности

- Требуется чистый рабочий Git-каталог: иначе `WORKTREE_DIRTY`.
- Точное соответствие `HEAD` запрошенному SHA: иначе `HEAD_CHANGED`.
- Конфигурация должна быть включена в текущий коммит и соответствовать фиксированной схеме; неизвестные поля, дубликаты JSON-ключей, пустые тесты и неправильные таймауты отклоняются.
- Пути к конфигурации, VERSION, CHANGELOG и рабочим каталогам должны оставаться внутри корня Git; пути с `..` и выходом через ссылки запрещены.
- Команды представлены **массивами аргументов**, `shell=False`; нет подстановки командной оболочки. Но сами команды могут выполнять произвольные действия, поэтому запуск только по явному разрешению в доверенном репозитории.
- Каждый шаг имеет лимит времени (1–900 секунд); результат содержит ID, тип проверки, код завершения и длительность. Вывод команд не включается в JSON, чтобы не публиковать случайные секреты.
- Проверка останавливается при первой ошибке, таймауте или невозможности запуска. После выполнения повторно проверяются HEAD и чистота Git.
- Инспектор не записывает в Git, не создаёт теги и не отправляет данные на remote. **Команды `--execute` могут менять файлы по своему назначению**; автоматический откат не реализован.

## Границы достоверности

`preflight_status=PASS` означает только проверку VERSION/CHANGELOG/состояния Git. `checks_status=PASS` означает, что **реально запущенные** объявленные команды вернули код 0 и не нарушили проверяемые инварианты. Если сборка явно не применима, поле `build_status=NOT_APPLICABLE`, а не PASS.

Компонент **не проверяет** корректность тестов по смыслу, подлинность внешних CI-логов, подпись коммита, наличие аннотированного тега, удалённый Git и GitHub Release. `release_readiness` всегда `NOT_VERIFIED` до появления контроллера завершающих стадий. Это **T09.02**, а весь T09 остаётся PARTIAL.

## Тестирование и интеграция CI

```bash
python -m unittest discover -s tests -v
```

Обязательный CI TESSERA выполняет только `--plan`. Испытания запуска команд с `--execute` проводятся на **временных Git-репозиториях** в модульных тестах. Реальные команды из чужого PR не запускаются автоматически.
