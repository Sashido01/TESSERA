# T09.08 — trusted catalog build and GitHub attestation

[Русский — оригинал](TRUSTED_BUILD.md) | **English — translation**

## What is actually distributed

TESSERA is a public Agent Skills catalog, **not an executable application**. T09.08 introduces a genuine source distribution: `TESSERA-catalog-vX.Y.Z.zip`, including runtime skill files, `LICENSE`, `README`, `VERSION`, and a deterministic `MANIFEST.json`. It is the **catalog** version, not a replacement for future independent per-skill versions (T16).

`tools/build_catalog_package.py` uses the Python standard library only. ZIP entries have deterministic timestamps, ordering, permissions, and file lists. The manifest contains byte lengths and SHA-256 hashes for all packaged files, the exact source commit SHA, and catalog version. Tests, caches, local paths, and transient data are excluded. Symlinks, unsafe paths, and missing required files are rejected.

This is a **real catalog build output**, so `release-checks.json` now declares a required build command instead of declaring builds inapplicable. Both existing test suites remain required.

## Real T09.10 incident and correction

On 24 November 2026, the user dispatched `build-attested-catalog.yml` at verified annotated `v0.0.19`. [GitHub Actions run #45347443989](https://github.com/Sashido01/TESSERA/actions/runs/45347443989) ended `completed/failure`: exact commit and annotated tag checks passed and 333+19 tests succeeded, but packaging failed with `BLOCKED: PACKAGE_RUNTIME_FILE_INVALID`. Sigstore attestation and artifact upload were skipped; there were zero Actions Artifacts.

**Root cause:** tests in `skills/microversion-release/tests/` import Python modules from `skills/microversion-release/scripts/*.py`. By default, Python writes `scripts/__pycache__/*.pyc`. The ZIP builder correctly rejects anything other than ordinary `.py` files in runtime `scripts/`. Previous PR CI packaged **before running tests**, so it did not exercise the signing workflow's **test-then-package** order.

**Correction:** both signing and validation jobs now set `PYTHONDONTWRITEBYTECODE: '1'`, and CI performs a second reproducible ZIP build in `dist/post-tests` after unit tests. Static security checks enforce both controls; a negative test retains the strict rejection of generated `__pycache__`. OIDC privileges, immutable action SHA pins, tag/ancestry checks and allowlisting are unchanged.

**Status:** passing main CI does not create a signature. A new signing workflow must be manually dispatched at a **newly confirmed annotated tag**, complete SUCCESS, and yield an actual ZIP whose digest, manifest and Sigstore attestation are independently verified. Do not rerun signing on `v0.0.19`; published historical refs must remain unchanged.

## Two distinct phases

1. **PR/CI**: execute tests, static signing-workflow checks, and a reproducible ZIP build, **without attestations, OIDC, or GitHub Release publication**. Failed CI blocks merging.
2. **After merge and an annotated release tag**: a separate `.github/workflows/build-attested-catalog.yml` is triggered **manually on the selected tag** using `workflow_dispatch`. It verifies VERSION, annotated tag object, exact commit and ancestry in `main`, reruns mandatory tests, builds the ZIP, generates a GitHub/Sigstore attestation, and uploads the actual package to GitHub Actions Artifacts.

All Actions use full commit SHAs. The signing workflow has **no `contents: write` permission**. Its job alone gets `id-token: write`, `attestations: write`, and `contents: read`. Pull Request checks never get signing permissions. No PAT or paid API is required.

## Updated pinned Actions

Both workflows use SHA-pinned `actions/checkout` v7.0.1 and `actions/setup-python` v7.1.0. The signing workflow additionally pins `actions/attest` v4.2.2 and `actions/upload-artifact` v7.0.2. All four declare Node.js 24. See the complete [pin inventory](GITHUB_SECURITY.en.md), enforced by `tools/check_actions_runtime.py`. This runtime upgrade does not create any attestation: the signing workflow still requires a deliberate dispatch on a verified annotated tag.

## Why dispatch is manual

The existing `validate.yml` creates tags after successful pushes to `main` with GitHub's normal `GITHUB_TOKEN`. GitHub does **not** trigger a second workflow on a push generated by `GITHUB_TOKEN`. Signing inside the `main` job would bind the attestation source ref to `refs/heads/main`, rather than the desired `refs/tags/vX.Y.Z`.

The safe sequence is a verified tag followed by separate `workflow_dispatch` **at that tag**. Future automation may be researched without PAT secrets or bypassing Rulesets.

## Safe CLI version for verification

Downloading an Actions Artifact and checking provenance requires `gh 2.102.0+`; older versions contained signer-workflow/source-ref matching bugs and unsafe symlink handling when downloading files. `core/release_provenance.py` now rejects outdated or unrecognized CLI versions. Check `gh --version` **before** manually downloading a ZIP; the ZIP inspector remains a separate offline integrity check. See [RELEASE_PROVENANCE](RELEASE_PROVENANCE.en.md).

## Commands

After the `main` CI and tag have both completed:

```bash
# Local build check only: no signature or publication.
python tools/build_catalog_package.py --repo . --output-dir dist --check-reproducible

# Start actual signing workflow at the verified annotated tag.
gh workflow run build-attested-catalog.yml --ref v0.0.14 -R Sashido01/TESSERA

# Once that workflow succeeds, obtain its Actions artifact.
gh run download <build-run-id> -R Sashido01/TESSERA -n tessera-catalog-v0.0.14

# Independently verify the extracted ZIP's signed provenance.
gh attestation verify TESSERA-catalog-v0.0.14.zip \
  --repo Sashido01/TESSERA \
  --source-ref refs/tags/v0.0.14 \
  --source-digest <full-release-commit-sha> \
  --signer-workflow Sashido01/TESSERA/.github/workflows/build-attested-catalog.yml \
  --deny-self-hosted-runners
```

Commands with `v0.0.14` are instructions to follow **after that tag is published**, not claims that the workflow already ran. Use actual run IDs and release SHAs. Never dispatch signing on a branch or an unrelated tag.

## Distinctions

- **GitHub Actions Artifact** is a workflow-run output with limited retention, **not a GitHub Release asset**.
- **GitHub attestation** signs the artifact provenance claim for specific bytes and workflow identity, **not TESSERA's final JSON evidence certificate**.
- A **signed catalog source ZIP** is a real distribution of Agent Skills, **not proof that programs consuming the skills work correctly**.
- The existing `core/release_provenance.py` T09.07 currently requires a published GitHub Release asset. It must not mistake the new Actions Artifact for one; connecting these delivery paths requires further work.

## Acceptance and limits

Unit tests cover deterministic packaging, manifest SHA-256, safe file inclusion, incorrect tags, dirty Git status, and static signing-workflow safety. GitHub CI independently runs the builder.

Until the signing workflow actually executes at a real annotated tag and its signed attestation is validated, **`SIGNED_ARTIFACT=NOT_VERIFIED`**. This stage creates no GitHub Release. Remaining work includes live signing and verification, a product decision on real Release publication, integration with Release Core and concurrent release coordination.
