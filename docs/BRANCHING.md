# Работа с ветками и Pull Requests в TESSERA

[**Русский — оригинал**](BRANCHING.md) | [English — перевод](BRANCHING.en.md)

## Принцип: одна цель — одна проверяемая поставка

**Новая ветка для каждого коммита, исправления или шага агента не нужна.** В проекте активны серверные Rulesets для `main` и релизных тегов, поэтому объединение изменений с `main` должно проходить через Pull Request и обязательный CI. GitHub защищает **целевую ветку и теги**, а не требует уникального имени ветки для каждой микроверсии.

Нормальный порядок: один короткоживущий рабочий branch на **одну логически связанную цель**, несколько технических коммитов и исправлений **в этой же ветке**, один Pull Request после готовности. По успешной приёмке — Squash and merge, затем автоматический аннотированный тег от утверждённого коммита `main`. После слияния рабочую ветку можно удалить; уже существующую историю `main` и опубликованные теги переписывать нельзя.

## Микроверсионность без лишних веток

- Релизная микроверсия назначается завершённому **самостоятельному проверенному результату**, а не промежуточному запуску теста, ошибке CI, доработке документа или исправлению до слияния.
- Промежуточные коммиты в пределах одной незавершённой цели допустимы без отдельных релизных тегов. **Финальный Squash-коммит**, проходящий CI, должен содержать согласованные `VERSION`, русскую и английскую версии CHANGELOG и все изменения завершённой цели.
- При обнаружении ошибок в CI чиним ту же рабочую ветку и обновляем тот же PR, не создаём новый branch и не увеличиваем версию только ради исправления.
- Когда действительно завершены **две независимые цели**, они могут потребовать двух последовательных микроверсий и двух выпусков. Не объединяем несовместимые изменения только ради сокращения количества PR.
- Релизным считается только подтверждённый коммит `main` с аннотированным тегом, указывающим именно на него.

## Почему не постоянная develop

При текущем Squash and merge постоянный `develop` потребовал бы дополнительных операций синхронизации с новым коммитом `main` после каждого слияния, а при неаккуратном сбросе возникал бы риск переписывания истории. Пока достаточно короткоживущей ветки на цель. Если работа будет параллельной у нескольких агентов, нужна отдельная безопасная схема координации, а не молчаливый `push --force`.

## Безопасность

Нельзя обходить защищённую `main`, отключать Rulesets ради ускорения, применять force-push к опубликованным тегам или выдавать рабочие коммиты за опубликованный релиз. Проверки из PR не должны выполнять команды неподтверждённой сборки с повышенными правами. Для автоматической публикации тега после Squash merge действует проверка текущего SHA `main` и неподвижности уже существующего тега.

**Примечание:** короткоживущая ветка — технический способ соблюсти серверную защиту, а не отдельная продуктовая версия. Политика микроверсий: [VERSIONING](VERSIONING.md). Фактические правила доступа: [GITHUB_SECURITY](GITHUB_SECURITY.md).

## Параллельные потоки

Разрешены независимые короткоживущие черновые ветки без назначения общей микроверсии; назначение происходит только в одном слоте интеграции от актуального main. Ошибка CI исправляется в той же ветке. Не создавай конфликтующие релизные PR и не переиспользуй PASS старого SHA. Ветки с активной работой сохраняются; после squash проверяй принятый результат, а не только ancestry. Подробности: [PARALLEL_WORKFLOW](PARALLEL_WORKFLOW.md).
