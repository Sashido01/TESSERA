# Обязательные теги Git для релизов

[**Русский — оригинал**](RELEASE_TAGS.md) | [English — перевод](RELEASE_TAGS.en.md)

## Что обязательно

Для **каждого завершённого релиза** `0.1.0`, `0.2.0`, `1.0.0` и т. д. обязательно существует **аннотированный** тег Git с читаемым русским описанием, который указывает точно на релизный коммит. Пока тег отсутствует или некорректен, релиз имеет статус `BLOCKED / RELEASE_NOT_TAGGED`; нельзя заявлять `COMPLETE`.

Для проекта с несколькими независимыми продуктами имена тегов могут включать префикс (`microversion-release/v0.1.0`). Префикс фиксируйте в политике проекта заранее. Для рабочих микроверсий `x.y.1`–`x.y.99` и `x.y.100+` теги создаются по политике конкретного проекта, но для `x.y.0` — обязательны.

## Прежде чем создавать тег

- Установите текущие Git HEAD, статус репозитория и версию.
- Убедитесь, что сборка и все обязательные проверки действительно прошли.
- Завершите фиксацию файлов релиза; тег должен указывать **на релизный коммит**, а не на промежуточный.
- Проверьте, что нужный тег ещё не занят и не указывает на другое изменение.
- Не выполняйте автоматический `git push`, если публикация не разрешена отдельно.

## Безопасные команды

Из корня каталога установленного навыка (путь к проекту передаётся явно):

```bash
python scripts/release_tag.py verify 0.1.0 --repo <project-root>
python scripts/release_tag.py create 0.1.0 --repo <project-root> --message "Релиз 0.1.0 — исправлен запуск приложения"
python scripts/release_tag.py verify 0.1.0 --repo <project-root>
```

Для монорепозитория:

```bash
python scripts/release_tag.py create 0.1.0 --repo <project-root> --prefix microversion-release/ --message "Релиз навыка 0.1.0 — проверено обновление версий"
```

Команда `create` создаёт **только локальный аннотированный тег Git**, не коммитит, не запускает тесты и не отправляет изменения в сеть. Повторное использование уже существующего тега допустимо только при его корректной аннотации и совпадении с HEAD; неподходящий тег не перезаписывается.

## Публикация на GitHub и другие remote

Если релиз объявлен **опубликованным**, то одного локального тега недостаточно: необходимо подтверждение разрешённого `push` соответствующего тега и идентичности коммита на remote. GitHub Release, архив и файлы сборки — отдельные результаты, их статус указывайте явно.

## Разрешение ошибок

- `RELEASE_NOT_TAGGED`: отсутствует тег, создан легковесный тег без аннотации, тег указывает на другой коммит либо аннотация пуста.
- Нет разрешения на запись: остановитесь, сообщите `BLOCKED`, не используйте обходные способы.
- Тег уже существует с другой привязкой: остановитесь, выясните конфликт, не используйте `--force`.
- Параллельные агенты: синхронизируйте релизные операции до создания тегов.

**Важное ограничение:** проверка корректного тега не заменяет проверки самой сборки и не является доказательством, что приложение работает.


Для привязки к результату ранее выполненных проверок передавайте полный SHA через `--expected-head <SHA>` в `create` и `verify`. Если SHA отличается от HEAD, операция блокируется. Даже без этого параметра `create` фиксирует текущий SHA до записи и явно передаёт его Git; проверяется неизменяемый объект аннотированного тега, прямой target commit и имя внутри объекта. Повторная сверка HEAD и ссылки обнаруживает наблюдаемое изменение. При конфликте после создания тег не удаляется и не перемещается автоматически; статус BLOCKED, нужна проверка конфликта. Это не атомарная блокировка параллельных писателей, не доказательство прохождения тестов и не полная защита от гонок.

Перед операцией требуется обычное окружение Git без внешнего перенаправления репозитория, пространства имён, объектов или подмены конфигурации через перечисленные переменные среды. При их наличии CLI блокируется, а не молча игнорирует настройки. Вызов из Git hook/нестандартной среды может требовать отдельного согласованного адаптера. Доверенность установленного Git, PATH, конфигурации выбранного репозитория (включая подписывающие программы и hooks) и файловой системы остаётся предпосылкой; это не sandbox.

Дочернему Git передаётся только фиксированный набор переменных запуска, путей, локальной идентичности и контекста подписания. Остальные переменные (включая токены и произвольные переменные приложения) не передаются; исходное окружение процесса не меняется. Конфигурация, требующая дополнительных переменных, может завершиться BLOCKED и требует отдельной проверенной интеграции. Это не изоляция от файлов, локальных signing helpers или сети.

Git выбирается только из абсолютных каталогов PATH; пустые и относительные элементы пропускаются, используется абсолютный разрешённый путь к git (git.exe на Windows). Каждый вызов ограничен 60 секундами, stdin закрыт, shell=False. Ошибки выполнения и таймауты не публикуют stdout/stderr Git. Суммарный текстовый вывод свыше 1 048 576 символов отклоняется после захвата; это не ограничение памяти/размера pipe. При таймауте создания сначала проверьте состояние тега: автоматического повтора/удаления нет. Интерактивная подпись может потребовать отдельного адаптера. Абсолютные каталоги PATH, Git и конфигурация всё ещё должны быть доверенными; подмена между вызовами, дочерние процессы, Windows junction и сетевая изоляция отдельно не проверены.
