# Обязательное исполнение — кандидат T13

[**Русский — оригинал**](ENFORCEMENT.md) | [English — перевод](ENFORCEMENT.en.md)

Для 0.1.0 владелец утвердил обязательное исполнение Microversion Release в Codex и DeepSeek Harness. Разделяем три наблюдения: загрузка навыка, выполнение событийного хука, независимый контроль результата. Никакое из них не подменяет остальные. Используй сначала новый одноразовый проект без remote; не изменяй существующие проекты, глобальные настройки, права, доверие к хукам или sandbox автоматически.

## Профиль базового проекта

Явно выбранный доверенный Git-root, существующий baseline commit, линейная история, корневые VERSION и CHANGELOG.md (заголовки ## MAJOR.MINOR.PATCH), опционально обязательный CHANGELOG.en.md через --bilingual. Проверяется до 32 новых коммитов: каждый должен изменить VERSION, применимые changelog и хотя бы один не-метаданный путь; следующий PATCH или разрешённый релизный рубеж, включая .100+. Для .0-релизов и релизного baseline нужен точный локальный аннотированный v-тег с непустой аннотацией. Проверка не создаёт тегов. Имена независимых тегов монорепозитория остаются отдельным контрактом release_tag.py/Release Core; данный базовый профиль их не проверяет.

`python -E -s -B <trusted-skill>/scripts/completion_gate.py check --repo <root> --baseline <full-sha> --bilingual`

Выход 0 STRUCTURE_VERIFIED — только структурная проверка; 1 BLOCKED. Ноль коммитов может быть допустим для читающей задачи, но не доказательство завершённой работы. Git status, ls-files -v (отказ при assume-unchanged/skip-worktree), HEAD и tag refs сверяются повторно. Игнорируемые файлы, полноценная вложенная история submodules, содержание тестов, подлинность baseline, атомарность, исчезающие гонки и доверенность локального Git не доказаны. Не sandbox. 30 с общий бюджет Git, до 5 с команда, 2 МиБ после захвата; нет жёсткой границы памяти или потомков. Все Git_* (кроме GIT_PAGER) в наследуемом контексте блокируются до запуска Git, в т.ч. #81. Не чистить окружение production для получения PASS. Граница может быть строже release_tag.py.

## Независимый владелец / controller

`guarded_run.py` из проверенной копии навыка **вне области записи агента**, запуск из обычного доверенного терминала владельца, отдельного от агентного sandbox. Это явная авторизация отдельной проверки, не обход sandbox и не доказательство Git-доступа из агента. Укажи абсолютные проверенные исполняемые файлы вне проекта (Windows только .exe; для Node CLI укажи проверенный node.exe и абсолютный script в argv), argv и timeout. Не запускай непроверенный проект или команду; тестовый executable/argv/контекст должны быть согласованы владельцем, тесты могут выполнять код проекта. Wrapper не расширяет и не меняет разрешения клиента.

Без --execute — PLAN_ONLY: только проверяет входы и baseline; не запускает агент/тесты. С --execute запускает именно указанный агент, проверяет Git независимо от его ответа/exit 0, затем согласованную команду тестов и повторно сверяет точный SHA, версию и объекты релизных тегов. Не принимает no-op по умолчанию; --allow-no-change только для явно читающей задачи. Не запускает тесты при ошибке агента/структуры. Любая ошибка, тайм-аут, нарушение структуры или изменение итогового состояния — BLOCKED, exit 1. ACCEPTANCE_CHECKS_PASSED, exit 0 — только две реально выполненные команды + структурный контроль; не RELEASED, не доказательство достаточности тестов или загрузки хука. Stdout — JSON; child output перенаправлен на stderr, который может содержать частные данные. Не публикуй stderr или argv. До 64 args / 32 KiB на команду, timeout агента 1–3600 c, тестов 1–900 c; завершение прямого процесса не гарантирует завершение потомков.

Пример **схемы** (подставить доверенные абсолютные пути, актуальные flags конкретного клиента и утверждённые команды; сначала без --execute):

```text
python -E -s -B <trusted-skill>/scripts/guarded_run.py
  --repo <root> --baseline <full-sha>
  --agent-exe <absolute-exe> --agent-arg=exec --agent-arg=--json
  --agent-arg <reviewed-prompt>
  --test-exe <absolute-python> --test-arg=-B --test-arg <trusted-test-entry>
```

Команда показана как перечень аргументов, не готовая shell-строка. Для Codex проверить версию, exec --help и выбранные права; для Harness — актуальный headless profile/CLI, не копировать Codex flags. Не добавлять flags отключения approval/sandbox или trust. GUI-сессия требует отдельно наблюдаемого хука и независимой проверки результата; wrapper не управляет чужим уже запущенным GUI.

## Stop adapter

Режим stop получает JSON до 256 KiB со stdin; требует event Stop, boolean stop_hook_active, абсолютный cwd совпадающий с явно заданным root. Не читает transcript, не использует переданный cwd для выбора репозитория и не печатает payload. Владелец задаёт отдельный marker в существующей доверенной приватной папке вне project root, доступной хуку для создания одного нового файла, но не агенту для удаления/подмены. Не выдавать дополнительные права ради маркера; если недоступен, adapter не просит повторного запуска, внешний gate остаётся блокирующим. Маркер создаётся эксклюзивно, не перезаписывается и не удаляется. Один маркер на один согласованный запуск, не повторно использовать. На первую неудачу возвращает decision:block (один запрос продолжения), затем continue:false со stopReason; при ошибке входа/маркера не запускает Git вне scope и не зацикливает. JSON exit 0 означает формат протокола, не PASS задачи.

Пример структуры hook config с проверенной **абсолютной** командой, сформированной владельцем под реальную оболочку клиента:
```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "<reviewed-python-and-absolute-script> stop --repo <root> --baseline <full-sha> --marker <private-new-marker> --bilingual",
            "timeout": 45
          }
        ]
      }
    ]
  }
}
```
Не копировать строку с placeholders буквально. Не подставлять произвольные значения из prompt или payload. Codex: проектный .codex/hooks.json, существующее содержимое не перезаписывать, review/trust через /hooks после просмотра точного определения; не обходить проверку доверия. Harness: экспериментальный @deepseek-ai/dsh-hooks-codex с configPath на проверенный файл, только отдельный профиль. Upstream Stop **всегда** передаёт stop_hook_active=false и игнорирует continue:false, при ошибке загрузки/выполнения хука агент может продолжить. Маркер ограничивает лишь повторный запрос продолжения, не доказывает veto. Внешний controller обязателен в обоих клиентах. Если отсутствует/падает hook, это NOT_VERIFIED для клиентской активации, не PASS. Не принимать успешную фразу агента.

Источники: [Codex Hooks](https://learn.chatgpt.com/docs/hooks), [Codex exec](https://learn.chatgpt.com/docs/non-interactive-mode), [Harness bridge](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/hooks-codex/README.md).

## Приёмка

Локально Linux Git 2.47.3 / Python 3.13.5 — 26/26 методов: 16 Git/Stop fixture и 10 реальных child-process wrapper fixture; Git blobs протестированных файлов совпали с кандидатом. Синтетические агенты и команды тестов не доказывают реальный Codex/Harness. Полный каталог/Windows требуют CI кандидата. Реальная приёмка каждого клиента: положительный 0.0.99 → 0.1.0 с точным тегом и согласованными тестами; отрицательные missing/lightweight/wrong tag, skip, dirty, no-op, ошибка/отсутствие хука, Git context unsafe, отказ теста и отсутствие повторного бесконечного продолжения. Наблюдать факт вызова хука в клиенте и код wrapper. Фиксировать версию/профиль клиента, exact tag/commit, вывод JSON и тестовые итоги без приватных данных. #81 закрывать только после доказанного least-privilege invocation и реальных Windows/Codex проб. Не включать в продуктивной среде до приёмки.
