# Микроверсии и человекочитаемые релизы

[**Русский — оригинал**](SKILL.md) | [English — перевод](references/SKILL.en.md)

## Когда использовать

Применяй этот навык для каждого проверяемого изменения программного проекта, подготовки коммита, тега, версии, выпуска релиза и перед объявлением задачи завершённой. Для исследования или ответа без изменений файлов новую версию не создавай. Не вызывай повторно без необходимости, если навык уже загружен в текущем ходе.

## Главный принцип

**Одно самостоятельное проверенное изменение — одна микроверсия.** Изменения только ради оформления этой же микроверсии не образуют новую микроверсию. Текущую версию извлекай из реального проекта и Git: никогда не угадывай её.

### Алгоритм номеров

- Для нового проекта начальная точка — `0.0.0`. Определи текущую версию из файлов проекта и Git; не угадывай.
- **Рабочая микроверсия** означает новый проверенный содержательный коммит: увеличивай PATCH на 1. Пока он не достиг 99, это обычный цикл `0.0.1`, `0.0.2`, …, `0.0.99`.
- **Релизный рубеж** возникает после PATCH=99. Если задача завершена и результат проверен, оформляй следующий релиз: `MAJOR.(MINOR + 1).0` (при MINOR<99) или `(MAJOR + 1).0.0` (при MINOR=99). Например, `0.0.99 → 0.1.0`, `0.1.99 → 0.2.0`, `0.99.99 → 1.0.0`.
- **Не прерывай незавершённую задачу ради рубежа .99.** Если она объективно не готова, продолжай фиксировать только реальные проверенные изменения: `.100`, `.101`, `.102` и далее столько, сколько необходимо. При первом трёхзначном PATCH, на котором задача действительно завершена и проверена, зафиксируй итоговое содержательное изменение, **затем** подготовь релиз `...0`.
- Например, `0.0.99 → 0.0.100` (работа продолжается), затем при успешном завершении на `0.0.100` — `0.1.0`. Если завершена только на `0.0.107`, после `0.0.107` выпускай `0.1.0`. Не выпускай его раньше завершения обязательных проверок.
- Не создавай искусственный `.100`, если задача уже завершена и проверена на `.99`. Не делай фиктивных коммитов ради достижения «красивого» числа.
- Если сборка релиза не прошла, оставайся на подтверждённой микроверсии, исправляй причину отдельными обоснованными изменениями (`.101`, `.102` и далее при необходимости); не называй релиз готовым до проверки.
- Номер выпуска не доказывает готовность приложения к промышленной эксплуатации. Особенно при `1.0.0` честно укажи известные ограничения.
- Для старого проекта с PATCH>99 не переписывай историю: продолжай PATCH+1; новый релиз готовь после завершения и проверки задачи с учётом действующей политики проекта.
- Только читающий калькулятор: `python scripts/next_version.py 0.0.99 --mode work` выводит `0.0.100`, а `python scripts/next_version.py 0.0.99 --mode release` выводит `0.1.0`. Режим release **только считает число**, а не устанавливает факт завершения задачи.

## Перед началом работы

1. Установи фактический Git-root, текущую ветку, статус Git, версии и теги, файлы метаданных, `AGENTS.md` и проектные правила выпуска.
2. Не считай сторонний репозиторий доверенным для автоматических изменений. Не выходи за разрешённую рабочую область; не выполняй push, reset, force и удаление Git-истории без отдельного разрешения.
3. Если проект использует несовместимую политику, не меняй её молча. Зафиксируй конфликт и согласуй миграцию. Прямо утверждённую пользователем новую схему применяй только вперёд, без переписывания истории.
4. Если точную текущую версию установить невозможно, сообщи `NOT_VERIFIED`, не подставляй догадку.

## Рабочий цикл одной микроверсии

1. Заверши конкретное изменение и опиши реально полученный результат.
2. Запусти необходимые тесты, сборки и проверки. При обязательной неуспешной проверке не выпускай релиз.
3. Повторно проверь Git; не захватывай чужие незавершённые изменения и не применяй `git add -A` без осознанного контроля файлов.
4. Вычисли следующий свободный номер в режиме work для рабочего изменения или release после рубежа, завершения задачи и необходимых проверок. Проверь отсутствие существующего тега и согласованность источников версии.
5. Точечно обнови только управляемые метаданные. Не изменяй упоминания старых версий в исторических документах, тестах и архивах.
6. Обнови краткую запись истории текущей микроверсии. Отдельный релиз `.0` готовь после последнего завершившего задачу содержательного коммита: выполни полную сборку и предусмотренные испытания, сформируй проверенные артефакты и понятное описание.
7. Для реального изменения создай содержательный коммит с микроверсией; последний проверенный рабочий коммит может быть `.100+`. После него допускается отдельный релизный коммит `.0` для сборочных и версионных метаданных. Не переписывай старые коммиты.
8. Создай локальный **аннотированный** Git-тег `vMAJOR.MINOR.PATCH` с понятным описанием и проверь его привязку к нужному коммиту. Отправка на remote, веб-релиз и публикация сборок разрешены только по действующей политике проекта.
9. Проверь итоговую версию, Git HEAD, состояние дерева, тег, CHANGELOG и артефакты. Объявляй COMPLETE только на основании реальных проверок.
10. При частичном завершении отдельно версионируй только самостоятельно законченные и проверенные части, остальное пометь PARTIAL или BLOCKED.

## Обязательное правило релизного рубежа

На рубеже `PATCH>=99 → следующий релиз ...0` нельзя ограничиться заменой цифр. Определи настоящую команду сборки проекта и выполни требуемые тесты; проверь результат и опиши его. Для проекта без сборки не выдумывай артефакт: обозначь RELEASE_BLOCKED или используй заранее согласованный режим документального релиза.

## Естественный язык

Подробные примеры: [references/STYLE.md](references/STYLE.md). При документировании проекта русский текст является оригиналом; англоязычную копию оформляй после русского текста, если это предусмотрено языковой политикой проекта.

- Пиши по-русски, конкретно и просто, если проект не требует другого языка.
- Коммит отвечает «что изменилось и зачем», а не «какую команду выполнил агент».
- Имя тега остаётся машинным (`v0.1.0`), человекочитаемое описание помещай в его аннотацию.
- Название релиза: `Версия 0.1.0 — <описание конкретного результата>`.
- CHANGELOG содержит только факты: что изменилось, как проверено и какие ограничения известны.
- Избегай `chore: bump version`, `misc fixes`, `улучшена система`, `оптимизирован функционал`, `AI-generated` и других пустых формулировок.
- Не выдавай тесты за пройденные без доказательств.

## Финальный отчёт

Укажи COMPLETE / PARTIAL / BLOCKED / NOT_VERIFIED, версию до/после, понятное описание изменений, реальные команды и результаты проверок, SHA коммита и тега (если созданы), статус сборки/публикации и ограничения. Если релиз не состоялся, назови причину. Не обещай фоновое продолжение работы.

## Безопасность и повторяемость

Не выпускай одно изменение повторно. Не изменяй существующие теги. При параллельных агентах и worktree нужна синхронизация релизных операций; без неё не проводи автоматический релиз. Не удаляй чужие изменения ради чистого Git. После сбоя должно быть возможно безопасно продолжить операцию.

**Ограничение:** SKILL.md — инструкция, а не обязательный фоновый обработчик. Автоматическое обнаружение зависит от агентной среды. Для строгого исполнения необходимы дополнительные правила проекта или событийная интеграция.
