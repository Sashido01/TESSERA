# Project Cleanup

[**Русский — оригинал**](SKILL.md) | [English — перевод](references/SKILL.en.md)

## Цель
Минимизировать физический объём и число ненужных объектов без потери функциональности, воспроизводимости, скорости разработки и восстановления. Очистка — отдельная проверяемая задача; меньший размер не важнее безопасности.

## Рабочий цикл
1. Зафиксируй явно выбранный корень, правила проекта и разрешённые действия. Не выходи за корень, не следуй ссылкам/reparse points, не затрагивай соседние проекты, глобальные кеши, профили или общий Git storage.
2. Выполни исходную [инвентаризацию](references/INVENTORY.md): логические байты, число файлов, крупнейшие области, кандидаты, пропуски и время. Измерь свободное место отдельно на целевом томе. Учитывай Git index, ignored/untracked, worktrees, submodules и открытые процессы. При неизвестном контексте — только чтение.
3. Раздели объекты на KEEP (источники, конфигурация, lockfiles, данные, модели, evidence, backups, текущие релизы), REVIEW (предположительно воспроизводимые кеши, старые сборки и временные файлы) и UNKNOWN. Имя, размер, возраст, расширение и игнорирование Git не доказывают ненужность.
4. При наличии двух явно предоставленных свежих Git-снимков опционально используй [PC02](references/CLEANUP_PLAN.md); REVIEW не означает разрешение удаления, а совпадение снимков не доказывает актуальность. Составь локальный точный план: каждый относительный путь/идентификатор, тип, объём, причина, подтверждение воспроизводимости, зависимости, занятость, срок хранения и способ восстановления. Проверяй содержимое разрешённой области только при необходимости; не публикуй приватные пути.
5. Если проект требует резервирования, проверь восстановление до удаления. Сверь Git status, текущий release, живые процессы, worktrees, свежесть плана и каждый объект непосредственно перед действием. Удаляй только однозначно разрешённые и проверенные объекты штатным способом; каталоги — только после инвентаризации всех потомков и отсутствия ссылок/чужих данных. Отказ политики или изменение объекта означает BLOCKED; не обходи запрет другим инструментом.
6. Проведи [Git и GitHub-проверки](references/GIT_STORAGE.md) отдельно. Не удаляй теги, историю, stash, evidence, релизы и CI-доказательства для уменьшения счётчика; не переписывай историю. Удаление веток координируй с Repository Workflow.
7. Повторно измерь те же метрики в том же объёме. Проверь исходники, git status, fsck по необходимости, целевые тесты, сборку/запуск и восстановление. Отделяй фактические освобождённые байты от логического размера удалённых файлов и оценок GitHub.
8. Введи профилактику по правилам проекта: выделенный ignored каталог временных данных, ограниченные кеши/логи и число старых сборок, срок хранения артефактов, проверка роста перед коммитом и после релиза. Повторяй быструю инвентаризацию на завершении работы; полную — периодически и при заметном росте. Не создавай фоновое расписание без согласия владельца.

## Границы
Помощник inventory.py только читает метаданные; cleanup_plan.py дополнительно читает явно предоставленные снимки Git, но не содержимое кандидатов. REVIEW никогда не означает разрешение удаления. Автоматического удаления, запуска Git/GitHub, изменения ignore или фонового планировщика в них нет. Сохраняй исходники и рабочие данные. Не применяй массовые destructive clean, prune, force-push, перепаковку или очистку reflog без отдельной проверенной политики и полномочий. При невозможности доказать безопасность оставь объект, отметь BLOCKED/UNKNOWN и продолжи независимую часть.

Итог: объём и количество до/после, выполненные действия, измеренная экономия, затраты на повторную сборку, сохранённое/пропущенное, результаты проверок, остаток долга и следующая инвентаризация.
