# TESSERA agent guidelines

[Русский — основной язык](AGENTS.md) | **English — translation**

TESSERA is a public library of portable Agent Skills. Canonical repository: `Sashido01/TESSERA`.

1. Read the README, repository rules, and existing skills before making changes. Do not confuse TESSERA with an application that consumes one of its skills.
2. Place each skill in `skills/<name>/SKILL.md`; the frontmatter `name` must match the directory. Follow the Agent Skills specification.
3. Keep skills independent. Place environment-specific integrations for Harness, Codex, or other tools separately, and never promise automatic activation without verification.
4. After changes, run `python tools/validate_skills.py`, `python tools/check_public_paths.py`, `python tools/check_translations.py`, `python tools/check_repository_version.py`, `python -m unittest discover -s tests -v`, and the tests of affected skills. Record actual results.
5. **The same microversioning rules apply to TESSERA itself, not only its skills.** The historical start is `0.0.0`; mandatory catalog microversioning begins at `0.0.1`. For every independently verified change, increment the root `VERSION` by PATCH+1 and update both changelogs in the same commit. At `.99`, release the next `.0` milestone only after task completion and required checks. If the task is unfinished, continue with `.100`, `.101`, and beyond. Never create dummy commits or rewrite older history. Details: [VERSIONING.en.md](docs/VERSIONING.en.md).
6. Write Git commits and release descriptions in clear, concrete **Russian**, following the canonical rules. Do not claim tests, builds, or publications that are not verified.
7. Do not publish secrets, private configuration, personal data, the owner's absolute working directories, or unrelated project files. Local paths may be used in the current environment but must never appear in public documentation, examples, commits, or release notes. Use placeholders such as `<project-root>` and `<skills-dir>`. Never force-push or rewrite other people's tags and history.
8. **Every TESSERA release and every individual skill release requires an annotated Git tag.** After CI succeeds for a `main` commit, an annotated `vX.Y.Z` catalog tag is created with a clear Russian description; individual skill tags may use `<skill>/vX.Y.Z`. Verify annotation and correct release-commit target. Without the required tag, report `BLOCKED / RELEASE_NOT_TAGGED`. Never move existing tags. Publishing a GitHub Release or changing remote repository settings is a separate action; a Git tag is not a published application.
9. Do not rewrite historical releases. If a skill's policy conflicts with an existing project's rules, preserve the project's constraints and report the conflict.
10. Before completion, report actual versions, commits, test results, changes, and remaining limitations.
11. **Language priority:** `README.md`, `AGENTS.md`, `SKILL.md`, other ordinary `*.md` files, and release communication are authored in Russian first. Translations use `*.en.md`. Keep English copies complete and updated within the same change. The skill's English reference lives at `references/SKILL.en.md`; never replace its canonical Russian `SKILL.md`. Check [docs/I18N.en.md](docs/I18N.en.md).
12. Keep the canonical skill portable across Codex, Harness, Claude Code, Hermes, and other Agent Skills-compatible environments. Do not require vendor-only fields in SKILL.md. Document platform-specific installation and mark unverified local execution as `NOT_VERIFIED`.
13. **Mandatory architecture decisions:** follow [docs/DEPENDENCIES.en.md](docs/DEPENDENCIES.en.md) and [docs/ROADMAP.en.md](docs/ROADMAP.en.md). Do not introduce third-party skill package managers into the approved architecture. Do not use NVIDIA SkillEvaluator Tier 2/3 or require paid AI APIs. GitHub CLI is the future preferred installer only after testing; Python is the minimal offline fallback. Plan one shared Release Core with thin host adapters, not four independent cores.
14. GitHub Rulesets and static CI checks are different controls. The PR → CI → squash merge → annotated tag workflow is verified. T08 remains PARTIAL because potentially destructive negative tag-update and bypass scenarios are not yet tested. Never run destructive tests on published tags. See [docs/GITHUB_SECURITY.en.md](docs/GITHUB_SECURITY.en.md).
15. For T09.02 use `core/release_preflight.py --plan` first. `--execute` is allowed only in trusted projects after explicit approval and review of `release-checks.json`. Never automatically execute commands supplied by untrusted Pull Requests; passing checks do not replace annotated tags or prove RELEASED. See [docs/RELEASE_PREFLIGHT.en.md](docs/RELEASE_PREFLIGHT.en.md).
16. T09.03: after validating an annotated tag, compare its object SHA on a trusted remote using `core/release_report.py --verify-remote` and generate a factual JSON/Markdown report. Never run `--execute-checks` without explicit approval; `evidence_status=PASS` must not be represented as application release readiness. See [docs/RELEASE_REPORT.en.md](docs/RELEASE_REPORT.en.md).
17. T09.04: independently verify GitHub Actions **only after the entire workflow has completed** with explicit `--verify-ci --github-repo <owner/repo> --run-id <id>`. Check exact commit SHA, workflow, and both required jobs; never introduce circular self-verification in a still-running job. Successful CI does not imply published software. See [docs/RELEASE_CI.en.md](docs/RELEASE_CI.en.md).
18. T09.05: verify GitHub Releases separately from tags and CI. Do not query the network by default; `--verify-publication` requires a trusted GitHub repository and matching Git remote. Never automatically create GitHub Releases or claim that asset metadata proves file bytes. `--format certificate` produces an unsigned deterministic SHA-256 evidence checksum, not a cryptographic attestation. See [docs/RELEASE_PUBLICATION.en.md](docs/RELEASE_PUBLICATION.en.md).
19. T09.06: `--verify-assets` requires explicit `--verify-publication`. Verify SHA-256 and size of **downloaded bytes**, not just GitHub digest metadata. Do not return PASS when no attached assets exist, do not allow arbitrary URLs or untrusted redirect hosts, and never publish a local owner's path. Even a matching SHA leaves `artifact_provenance` and `release_readiness` NOT_VERIFIED. See [docs/RELEASE_ASSETS.en.md](docs/RELEASE_ASSETS.en.md).
20. T09.07: do not mistake a SHA-256 match for independent attestation. Use only official `gh attestation verify` via explicit `--verify-provenance` with verified release asset metadata, `--artifact-file`, `--signer-workflow`, exact source commit SHA and Git tag. If there is no real signed published artifact, report NOT_VERIFIED; never create a fake GitHub Release. The final JSON certificate itself remains unsigned. See [docs/RELEASE_PROVENANCE.en.md](docs/RELEASE_PROVENANCE.en.md).
21. Git branches: one short-lived branch per coherent goal and one verifiable Pull Request. Fix CI failures **in the same** branch; do not create a new one per intermediate change. A completed and accepted `main` result receives the next microversion and mandatory tag. See [docs/BRANCHING.en.md](docs/BRANCHING.en.md).
22. T09.08: `tools/build_catalog_package.py` produces a deterministic **catalog** ZIP, not an independent version of a nested skill. Trusted attestation requires manual `workflow_dispatch` on a verified annotated tag via [build-attested-catalog.yml](.github/workflows/build-attested-catalog.yml). No PR signing and no automatic GitHub Release. Without a real signing run status remains NOT_VERIFIED. See [docs/TRUSTED_BUILD.en.md](docs/TRUSTED_BUILD.en.md).
23. T09.09: verify actual ZIP bytes with `tools/verify_catalog_package.py`, using independently established version and full source commit SHA. PASS demonstrates only internal consistency against the manifest, not origin, signing, or publication. Never extract or execute archive contents. See [docs/CATALOG_VERIFICATION.en.md](docs/CATALOG_VERIFICATION.en.md).
24. T09.10: do not use `gh attestation verify` or `gh run download` from GitHub CLI older than `2.102.0`: disclosed vulnerabilities affected signer/source-ref matching and symlink downloads. `core/release_provenance.py` must reject outdated or unknown versions. Never substitute mocked CLI responses for real signing, artifact bytes, and independent acceptance. See [docs/RELEASE_PROVENANCE.en.md](docs/RELEASE_PROVENANCE.en.md).

25. T11.01: use pinned upstream `skills-ref` with SHA-256-locked dependencies in addition to the TESSERA validator. Format compliance does not demonstrate successful agent-host activation. Upstream marks its reference library as demonstration-only; never use it as the sole production control. See [docs/AGENT_SKILLS_STANDARD.en.md](docs/AGENT_SKILLS_STANDARD.en.md).

26. T08.01: do not replace pinned GitHub Action SHAs with moving `@vN` tags, or revert to deprecated Node.js 20 Actions. `tools/check_actions_runtime.py` must reject unknown or changed actions in both validation and signing workflows. Review official release, SHA, runtime, and full CI before changes; this does not prove actual signing. See [docs/GITHUB_SECURITY.en.md](docs/GITHUB_SECURITY.en.md).

27. T11.02: use SHA-256-verified official `gh` only for `gh skill publish --dry-run` on a temporary `skills/` copy with no GitHub remotes, inherited tokens, or user configuration. Never run non-dry-run `gh skill publish` or `--fix` in CI. Check valid/invalid cases and unchanged file bytes; local PASS does not establish real publication. See [docs/GH_SKILL_PUBLISH_DRY_RUN.en.md](docs/GH_SKILL_PUBLISH_DRY_RUN.en.md).

28. T10.01: low-level InstallLocal lacks its own overwrite check; `gh skill install --from-local` invokes checkOverwrite. A target-existence check before invoking `gh` is mandatory, and tests may write only to a temporary isolated profile and destination. `--pin` and `--from-local` are mutually exclusive; never claim a local copy is tag-pinned. Remote SHA/tag installation belongs to T10.02. See [docs/GH_SKILL_INSTALL.en.md](docs/GH_SKILL_INSTALL.en.md).

29. T09.10.01: signing runs Python tests before packaging. Require `PYTHONDONTWRITEBYTECODE=1` in both signing and validate jobs; main CI must additionally build a reproducible ZIP **after** tests. Never allow `scripts/__pycache__` into signed ZIP or weaken the package allowlist. This fix is not evidence of a Sigstore signature. Actual failed run: [Actions 45347443989](https://github.com/Sashido01/TESSERA/actions/runs/45347443989); [TRUSTED_BUILD](docs/TRUSTED_BUILD.en.md).
30. T09.10 COMPLETE: [live v0.0.21 acceptance](docs/TRUSTED_BUILD.en.md) verifies one specific signed ZIP. Never inherit `SIGNED_ARTIFACT=PASS` for a new SHA or tag. Subsequent packages need separate download, SHA-256, manifest and independent Sigstore verification with a safe `gh` version. An Actions Artifact is not a GitHub Release.
31. T10.02: use fully qualified refs/tags/vX.Y.Z and an independently verified commit SHA, not an ambiguous short ref (branches take precedence). Compare expected Git tree and installed files in a fresh temporary directory. Only a read-only CI token; do not pass it to Git or print raw CLI errors. Never use --force or --unpin in a user profile. See [docs/GH_SKILL_INSTALL.en.md](docs/GH_SKILL_INSTALL.en.md).
32. T10.03.01: never apply native gh skill update --unpin/--all to user profiles without checking local edits: CLI replaces directory contents. Test exact re-pin through separate staging, complete snapshots, backup and verified rollback in disposable environments. Never claim crash recovery or race protection. [GH_SKILL_INSTALL](docs/GH_SKILL_INSTALL.en.md).
33. T10.03.02: skill names must be globally unique in a flat install directory; source namespaces do not create separate destination folders. Verify refs/tags/<skill>/vX.Y.Z together with commit and skill tree. Never publish fixture tags; local installation proves neither remote pin nor T16. [GH_SKILL_INSTALL](docs/GH_SKILL_INSTALL.en.md).
34. T12.01: only pinned NVIDIA SkillEvaluator 1.2.0 base wheel with hash-locked dependencies; call tier1 PATH --no-llm --checks schema,quality. Never run generic validate, LLM, Tier 2/3, or install extras. Do not equate execution PASS with quality or full Tier 1 PASS. [Documentation](docs/NVIDIA_TIER1.en.md).
35. T12.02.01: retain original NVIDIA scores and findings; localization adds language alternatives without disabling rules or changing weights/threshold. Static harness-check does not prove client execution. Never log raw PII, paths or report lines. Audit external scanners separately. [Documentation](docs/NVIDIA_STATIC_REVIEW.en.md).

## Continuous parallel work (25 November 2026 decision)

Each cycle reconcile main, tags, PR/CI, then infrastructure and every approved skill. WAIT_CI/WAIT_OWNER do not stop independent tasks. Short-lived draft branches without assigning the next shared VERSION are permitted; one integration slot, final metadata assigned from current main. GitHub speed is a measurable criterion; prefer native GitHub/Git features and fully support local projects without GitHub. Avoid excess complexity, mandatory external services and paid APIs. Do not weaken required checks. Review debt, open tasks, branches, worktrees, PRs, CI and tags at start and after acceptance; close only with evidence. Active branches are not clutter. Third skill Repository Workflow is approved. See [process](docs/PARALLEL_WORKFLOW.en.md), [debt](docs/TECHNICAL_DEBT.en.md), [research](docs/RESEARCH_REGISTER.en.md).

## Continuous storage hygiene (27 November 2026)

The fourth skill [Project Cleanup](skills/project-cleanup/references/SKILL.en.md) is authorized. At each completed stage check growth; after releases and periodically perform full inventory of the selected local project and separately Git/GitHub storage. Keep private reports in dedicated ignored `/.tessera-local/` or system temporary storage, never commit them. Measure first, remove only unambiguously unnecessary authorized objects, then remeasure and rerun checks. Do not destroy unique worktrees, current builds, user data, evidence, tags or history; never bypass a deletion-policy refusal. CI tests the committed tree for generated paths, non-source entries and a 1 MiB per-blob source-catalog budget. Changing the budget is a separate verified decision; do not disable the test to pass CI.
