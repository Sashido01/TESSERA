# TESSERA agent guidelines

[Русский — основной язык](AGENTS.md) | **English — translation**

TESSERA is a public library of portable Agent Skills. Canonical repository: `Sashido01/TESSERA`.

1. Read the README, repository rules, and existing skills before making changes. Do not confuse TESSERA with an application that consumes one of its skills.
2. Place each skill in `skills/<name>/SKILL.md`; the frontmatter `name` must match the directory. Follow the Agent Skills specification.
3. Keep skills independent. Place environment-specific integrations for Harness, Codex, or other tools separately, and never promise automatic activation without verification.
4. After changes, run `python tools/validate_skills.py`, `python tools/check_public_paths.py`, `python tools/check_translations.py`, `python tools/check_repository_version.py`, `python -m unittest discover -s tests -v`, and the tests of affected skills. Record actual results.
5. **The same microversioning rules apply to TESSERA itself, not only its skills.** The historical start is `0.0.0`; mandatory catalog microversioning begins at `0.0.1`. For every independently verified change, increment the root `VERSION` by PATCH+1 and update both changelogs in the same commit. At `.99`, release the next `.0` milestone only after task completion and required checks. If the task is unfinished, continue with `.100`, `.101`, and beyond. Never create dummy commits or rewrite older history. Details: [VERSIONING.en.md](docs/VERSIONING.en.md).
6. Write Git commits and release descriptions in clear, concrete **Russian**, following the canonical rules. Do not claim tests, builds, or publications that are not verified.
7. Do not publish secrets, private configuration, personal data, the owner's absolute working directories, or unrelated project files. Local paths may be used in the current environment but must never appear in public documentation, examples, commits, or release notes. Use placeholders such as `<project-root>` and `<skills-dir>`. Never force-push or rewrite other people's tags and history.
8. **Every TESSERA release and every individual skill release requires an annotated Git tag.** After CI succeeds for a `main` commit, an annotated `vX.Y.Z` catalog tag is created with a clear Russian description; individual skill tags may use `<skill>/vX.Y.Z`. Verify annotation and correct release-commit target. Without the required tag, report `BLOCKED / RELEASE_NOT_TAGGED`. Never move existing tags. Publishing a GitHub Release or changing remote repository settings is a separate action; a Git tag is not a published application.
9. Do not rewrite historical releases. If a skill's policy conflicts with an existing project's rules, preserve the project's constraints and report the conflict.
10. Before completion, report actual versions, commits, test results, changes, and remaining limitations.
11. **Language priority:** `README.md`, `AGENTS.md`, `SKILL.md`, other ordinary `*.md` files, and release communication are authored in Russian first. Translations use `*.en.md`. Keep English copies complete and updated within the same change. The skill's English reference lives at `references/SKILL.en.md`; never replace its canonical Russian `SKILL.md`. Check [docs/I18N.en.md](docs/I18N.en.md).
12. Keep the canonical skill portable across Codex, Harness, Claude Code, Hermes, and other Agent Skills-compatible environments. Do not require vendor-only fields in SKILL.md. Document platform-specific installation and mark unverified local execution as `NOT_VERIFIED`.
13. **Mandatory architecture decisions:** follow [docs/DEPENDENCIES.en.md](docs/DEPENDENCIES.en.md) and [docs/ROADMAP.en.md](docs/ROADMAP.en.md). Do not introduce third-party skill package managers into the approved architecture. Do not use NVIDIA SkillEvaluator Tier 2/3 or require paid AI APIs. GitHub CLI is the future preferred installer only after testing; Python is the minimal offline fallback. Plan one shared Release Core with thin host adapters, not four independent cores.
14. GitHub Rulesets and static CI checks are different controls. The PR → CI → squash merge → annotated tag workflow is verified. T08 remains PARTIAL because potentially destructive negative tag-update and bypass scenarios are not yet tested. Never run destructive tests on published tags. See [docs/GITHUB_SECURITY.en.md](docs/GITHUB_SECURITY.en.md).
15. For T09.02 use `core/release_preflight.py --plan` first. `--execute` is allowed only in trusted projects after explicit approval and review of `release-checks.json`. Never automatically execute commands supplied by untrusted Pull Requests; passing checks do not replace annotated tags or prove RELEASED. See [docs/RELEASE_PREFLIGHT.en.md](docs/RELEASE_PREFLIGHT.en.md).
16. T09.03: after validating an annotated tag, compare its object SHA on a trusted remote using `core/release_report.py --verify-remote` and generate a factual JSON/Markdown report. Never run `--execute-checks` without explicit approval; `evidence_status=PASS` must not be represented as application release readiness. See [docs/RELEASE_REPORT.en.md](docs/RELEASE_REPORT.en.md).
17. T09.04: independently verify GitHub Actions **only after the entire workflow has completed** with explicit `--verify-ci --github-repo <owner/repo> --run-id <id>`. Check exact commit SHA, workflow, and both required jobs; never introduce circular self-verification in a still-running job. Successful CI does not imply published software. See [docs/RELEASE_CI.en.md](docs/RELEASE_CI.en.md).
18. T09.05: verify GitHub Releases separately from tags and CI. Do not query the network by default; `--verify-publication` requires a trusted GitHub repository and matching Git remote. Never automatically create GitHub Releases or claim that asset metadata proves file bytes. `--format certificate` produces an unsigned deterministic SHA-256 evidence checksum, not a cryptographic attestation. See [docs/RELEASE_PUBLICATION.en.md](docs/RELEASE_PUBLICATION.en.md).
19. T09.06: `--verify-assets` requires explicit `--verify-publication`. Verify SHA-256 and size of **downloaded bytes**, not just GitHub digest metadata. Do not return PASS when no attached assets exist, do not allow arbitrary URLs or untrusted redirect hosts, and never publish a local owner's path. Even a matching SHA leaves `artifact_provenance` and `release_readiness` NOT_VERIFIED. See [docs/RELEASE_ASSETS.en.md](docs/RELEASE_ASSETS.en.md).
20. T09.07: do not mistake a SHA-256 match for independent attestation. Use only official `gh attestation verify` via explicit `--verify-provenance` with verified release asset metadata, `--artifact-file`, `--signer-workflow`, exact source commit SHA and Git tag. If there is no real signed published artifact, report NOT_VERIFIED; never create a fake GitHub Release. The final JSON certificate itself remains unsigned. See [docs/RELEASE_PROVENANCE.en.md](docs/RELEASE_PROVENANCE.en.md).
